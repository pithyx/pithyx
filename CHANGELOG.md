## [1.0.0-beta.1] - 2026-10-11

The first beta, codename Pyxis (D345): the NAS core, the file services, the app runtime with the Store, the installer and the updater.

### Known limitations

- The box's certificate authority keeps no revocation list, and Let's Encrypt is not built in; the setup step "Trust this device", passkeys and the service worker come later.
- Pool encryption (ZFS native, key vault) is not built, so no real data belongs on a beta box that needs encryption.
- Every elevated app right is refused with `app.elevated.unsupported`: an app that asks for `host.network`, `host.pid`, a device, a capability, `docker.socket` or `host.full` cannot be installed.

### Added

- Home folders (D348): every user gets a private home folder on the home pool, which only the user and the administrators can open. Users see it as `home`: first in Files (which opens there), as the SMB share `home` and as the folder `home` over SFTP, WebDAV and FTP; administrators also see every home as `homes`. A home has its own recycle bin (except in the SMB share `homes`) and is never granted to others or shown under Shared folders; apps see only the user's own. New page Settings > **Home folders**: the home pool (the first pool with the Pithyx layout until you pick another), moving every home to another pool as a job, a default quota and a quota per user, and the homes of deleted users. Deleting a user now asks whether to keep the home (renamed to `<name>.deleted-<uid>`), move its files into a shared folder, or delete it after typing the user name. `DELETE /api/users/{id}` takes `home`, `shareId` and `confirm` and answers with the job; new API under `/api/homes`, migration 0031, error codes `homes.*`; `home` is a reserved name for shared folders. The SDK's `ShareInfo` gets `kind`.
- Reverse proxy (D347): Settings > **Reverse proxy** serves your own domains on ports 443 and 80 while the box stays on 7484. Proxy hosts forward their domains (also `*.` wildcards) to an http or https target, with a certificate per host from the box's authority or uploaded, chosen by SNI; WebSockets, HTTP/2, unbuffered streaming, force HTTPS, optional HSTS, `X-Forwarded-*`, the `Host` to send, own request and response headers, an upload limit and timeouts; allowed and denied addresses, Basic Auth and the Pithyx sign-in (a host behind the box's accounts, users and groups, ended with the box session); a status check of the target and an access log per host in the Log Center (`proxy/<domain>`). Redirect hosts send domains to an address with 301, 302, 307 or 308. Streams forward a TCP or UDP port, and the firewall opens it. Names without a host still go to 7484, or get 404 if you choose so. Applies without a restart; new backup part Reverse proxy. API under `/api/system/proxy/` and `POST /api/proxy/tickets`, migration 0030, error codes `proxy.*`. A development build listens on the proxy ports of `PITHYX_DEV_PROXY_PORTS`.
- HTTPS (D346): the web interface, WebDAV and FTPS speak TLS 1.2 and 1.3 with HTTP/2 on port 7484; ports 80 and 443 redirect to `https://<host>:7484` (80 still answers `/api/install-id` for the installer), and plain `http://` on 7484 is redirected to `https://` on the same port. No HSTS. The box is its own certificate authority: a root (ECDSA P-384) and an intermediate (ECDSA P-256) limited by Name Constraints to local names and private addresses unless an administrator creates an unrestricted one, and a server certificate for the host name, `<host>.local`, the search domains and every address, issued again when they change and 30 days before it ends. The installer's live system stays on plain HTTP. FTPS presents the box's certificate instead of its own self-signed one.

- The proxy to app backends (A13, D303, D316, D323): `/apps/<id>/api/...` and `/apps/<id>/api-<name>/...` reach the app's backend through YARP's forwarder in the daemon. A request needs a backend token (`Authorization: Bearer` or `?pithyx-token=`) and a WebSocket a one-time ticket for its endpoint (`?pithyx-ticket=`); a cookie never counts, and every request checks the session, the user and the app's grant again. The backend gets the request without `Cookie`, `Authorization`, `Forwarded`, the `pithyx-*` parameters and any incoming `X-Pithyx-*` or `X-Forwarded-*` header, and with `X-Pithyx-User`, `X-Pithyx-User-Id`, `X-Pithyx-Groups`, `X-Pithyx-Admin`, `traceparent` and `X-Forwarded-Prefix`, `-For`, `-Host` and `-Proto`; answers lose `Set-Cookie` and carry the frontend's sandboxing policy. Preflights from a sandboxed window (`Origin: null`) are answered by the proxy, others refused. Open WebSockets close on a sign-out, a password reset, a deactivation, a revoked grant, a disabled or removed app and a stopped backend. Without a running backend the answer is 503 with the new error code `app.backend.unavailable`.

- Deleting a user cancels the user's queued and running jobs and drops its jobs and notifications from the daemon's memory. Users created in user management take their uid as their id, so a user id is never given out again and a new user can never see what belonged to a deleted one.
- A pool whose fill level hovers around 80 or 90 percent notifies once: a capacity alert counts as gone, or as calmed down, only once the pool is 5 points below the threshold. An alert of a pool that was exported or destroyed is dropped without a "resolved" notification.
- A pool can be created again under the name of a destroyed or exported one. Its root is not mounted, so ZFS had left the mount points of its datasets (`/<pool>/homes`, `/<pool>/.pithyx/...`) as empty folders on the system disk, and `zpool create` then failed with "mountpoint exists and is not empty". After a destroy or export the daemon now removes those folders, only when they are empty and only the pool's own mount points and the folders between them.
- Destroying a pool runs in the background: the dialog closes as soon as the job started, the pool's card says "Being deleted" until it is gone, and the notifications say when it is done or why it failed. The other pool actions can be closed while they run, too. A storage command of a plan that does not finish in time (for example a `zpool destroy` waiting in the kernel for a disk that stopped answering) now ends the job with the new error code `storage.command.timed_out` instead of an unexpected error. On a healthy pool `zpool destroy` takes well under a second on the dev VM; the long wait in a test came from a pool whose disks had been pulled, which the daemon refuses to destroy since the disk failure fix (`storage.pool.disks_missing`).
- The wallpaper draws its boxes like the logo in the menu button, with the lid closed and a narrow gap, instead of the lid floating far above the box.
- Toasts of notifications disappear when the notification panel opens, and none appear while it is open; toasts stay 5 seconds instead of 8.
- The taskbar clock no longer looks like a button: it had a hover effect and took the keyboard focus, but opens nothing.
- The About attribution, NOTICE, README and SECURITY link to `github.com/pithyx/pithyx` instead of the old repository name.
- A storage alert's mute could stay in the database for a moment after the alert went away, when the background check and a request refreshed the alerts at the same time; refreshes now run one at a time.
- The language switch on the sign-in and setup screens is a list of our own in the theme's colors instead of the native select, whose list was white on white in dark mode; it works with arrows, Home, End, Enter, Space, Escape and Tab (ARIA listbox).
- After loading or reloading the desktop, no element has focus; the Pithyx menu button takes it only when the last window closes or minimizes, and Tab reaches it as before.
- The desktop wallpaper draws its boxes with the logo's geometry (lid 16 units above the box) instead of a lid lifted too high, and the logo in the Pithyx menu button is larger (38 instead of 26 px).
- The daemon's start message names the port it actually listens on (it said 7484 with `PITHYX_DEV_PORT` set).
- A right-click while a context menu is open (on the desktop or in Files) showed the browser's menu instead of opening Pithyx's menu at the new point: the menu's underlay took the click. It now moves the menu there, or to the menu of whatever lies at that point; on a sticky note's text it only closes the menu. Touch long presses and the keyboard work as before.
- A shared folder whose pool is gone, stopped or not mounted is no longer "not found", and Files never lists or writes into its empty mount point on the system disk: the file service answers `fs.share.unavailable` with the reason, `GET /api/shares` and the SDK's `files.shares` mark the share as `unavailable` (`poolMissing`, `poolUnavailable`, `notMounted`), and Files shows "Not available" next to it. When its pool comes back, `shares/list` announces a new revision and Files reads the shares and the open folder again, so the listing recovers without a reload.
- Deleting a shared folder, and every other share or dataset plan, no longer ends in the SDK's request timeout when ZFS does not answer: a plan waits at most 10 seconds for the ZFS state it reads and then answers `storage.zfs.unavailable`, which says that a pool may be waiting for missing disks. A plan that destroys a dataset now needs a fresh snapshot list; with a stale one it could have destroyed a snapshot it did not list.
- Used and free space of pools, shared folders and datasets, and the fill level alerts at 80 and 90 percent, follow uploads and file jobs: writes raise no pool event, so the file service tells the daemon (an upload, a copy, move, delete, restore or recycle bin job that ended, the recycle bin's cleanup), which reads the pools again 6 seconds after the last write, once ZFS has synced them, and at least every 30 seconds during a long run of writes. Writes over SMB or SFTP show with the next pool read.
- A disk pulled out of a running box degrades its pool at once: without ZED, ZFS notices a missing disk only on its next write, so the daemon now derives the pools' health from the connected disks as well (a leaf whose device is gone is `REMOVED` with `missing: true` and the serial it was last seen with; its mirror, RAID-Z and pool degrade as ZFS would), raises the alerts `storage.alert.diskMissing` and, for a pool whose I/O ZFS suspended (read from `/proc/spl/kstat/zfs/<pool>/state`, which never blocks), `storage.alert.poolSuspended`. When the disk is connected again, the daemon brings it back with `zpool online` (and resumes a suspended pool with `zpool clear` once all its disks are back), once per disk change; ZFS resilvers what it missed and the alerts clear. Other pools are not affected, and the Storage app shows the disk as "Not connected".
- Destroying or exporting a pool whose disks are gone no longer hangs every pool until a reboot: `zpool destroy` on a pool that lost a vdev suspends it and waits in the kernel while holding the lock every other `zpool` command needs. Such plans are refused (`storage.pool.disks_missing`, `storage.pool.suspended`) when shown and again right before the command runs. Pool reads run one at a time, so a hanging `zpool` no longer piles up processes, and a failed read keeps the last state with the current disks applied.
- Dev VM: `tools/dev-vm/integration.sh` pauses the dev daemon on 7484 while the tests run, so it no longer changes their throwaway pools, and finds `losetup` under `sudo`.
- Creating a pool could fail with "dataset already exists" when the daemon's thumbnail cache setup created the pool's cache dataset between the steps of its layout. Creating the cache dataset now succeeds when it exists already.
- Importing a pool for use after its read-only preview failed with `storage.plan.stale` (found on the dev VM): the disks of a pool imported read-only are not probed, and after the plan's export step they are, so their signatures looked changed. Import steps now compare serial, size and partitions, not the ZFS labels they expect.
- Destroying a shared folder's dataset (and renaming a dataset, exporting or destroying a pool) failed with "pool or dataset is busy" while a Files window showed a folder in it (found on the dev VM): the live folder view held a handle on the folder. Such plans now close the daemon's own handles below the mount points they unmount before the first command, and the open Files window is told the folder is gone.
- A subscriber a topic refuses no longer counts as a subscriber, so it cannot make the daemon sample or watch for events it would never receive.
- Nullable nested objects in the OpenAPI document are marked nullable, so the generated client types them as `null | {...}`.
- A daemon started on a database that a newer daemon wrote (schema versions it does not know) exited with code 1 and no output, and the dev unit restarted it forever. It now logs the database, the unknown versions and what to do, flushes the log, and exits with its own code 65; the unit does not restart it (`RestartPreventExitStatus=65`) and gives up after five failed starts in two minutes. Other database failures at startup are logged too.
- `tools/dev-vm/install-dev-daemon.sh` builds as the calling user also under `sudo`, so the checkout gets no root-owned files, and refuses a checkout that already has some. `--from <checkout or worktree>` runs the unit from any checkout, for example a pull request's worktree. Before stopping anything it checks the database's schema versions against the checkout (and names a worktree that knows them), lists the unit or process it would stop on port 7484 and asks (`--yes` to skip the question).

- An open WebSocket whose session expired could stay open for good when the clock passed the expiry between the session check and its timer (a clock jump, or a slow check); the next check now ends it.
- `tools/fixtures/anonymize.ts` keeps the recorded text instead of rewriting the JSON, so 64-bit ZFS GUIDs stay exact; the build-time OpenAPI run no longer reads the build machine's disks.
- The first page of a large folder no longer waits for the whole folder to be sorted: it is selected directly (about 80 ms instead of 124 to 226 ms for 100,000 entries on the dev VM), and the full order is built in the background for the pages after it. The old sort's speed depended on how the JIT had tuned shared string code for the rest of the process, which made the listing budget test flaky.
- A finished job could read as finished in memory (API) while its row still said running; the final state is now written to the database first.
- Unsubscribing from a topic acknowledged before the daemon stopped the work behind it (for example a folder watch); the work now stops first.
- Uploading and dropping files in Files failed outside a secure context (`crypto.randomUUID is not a function` when the box is reached as `http://<address>:7484`).
- Opening the account menu or the start menu's power menu can no longer sign you out by accident. A menu that opened while its button moved could sit under the pointer, and releasing the button then picked "Sign out"; "Sign out" now needs a press that starts on it. The taskbar also takes no presses while it slides in after sign-in, and it slides in only once instead of again after every move to another screen edge.

### Security

- The command log no longer records the output of commands that print secrets: creating a configuration backup ran `pdbedit -L -w` and wrote every user's NT password hash into the Log Center and the log files at Info level. The output of `pdbedit`, `smbpasswd` and `chpasswd` is now always masked, and other callers mark secret output per command (the catalog deploy key's `ssh-keygen`).
