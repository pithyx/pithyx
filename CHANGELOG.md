# Changelog

## [Unreleased]

### Added

- Snapshots (step 8): manual snapshots and schedules per dataset (hourly, daily, weekly, monthly; off by default, keeping 24, 7, 4 and 6) named `pithyx-<schedule>-<utc>`, with a retention that only ever deletes snapshots Pithyx took, never held ones, never ones dated in the future, and always keeps the newest, also after clock jumps. Holds, delete after typing the name, and rollback after typing the dataset name with every newer snapshot listed. `GET`/`POST /api/storage/snapshots` and their delete, hold, release, rollback and schedule endpoints, administrators only; migration 0008.
- Previous versions in Files: the context menu lists the versions of a file or folder in the share's snapshots (read from `.zfs/snapshot`, no command runs) and restores one next to the current one or over it. `GET /api/files/{shareId}/versions`, `POST /api/files/{shareId}/versions/restore`, and the SDK methods `files.versions` and `files.restoreVersion` (permission `files.shares`).
- Storage health: alerts derived from the pools and SMART (pool degraded or faulted, data errors, scrub errors, fill level at 80 and 90 percent, SMART failures and warnings) stay until their cause is gone; administrators can mute them but not delete them. The most severe unmuted critical alert shows as a desktop banner, all of them in the notification center. SMART is read with `smartctl -n standby`, never waking a disk; virtual disks are shown as having no SMART data. Scrubs on demand and monthly, SMART self-tests weekly (short) and monthly (long), skipped while a disk sleeps. `GET /api/storage/alerts`, mute endpoints, scrub and schedule endpoints, and the topic `storage/alerts`, administrators only; migration 0009.
- Pools from the Settings app (step 8): a wizard chooses the disks, compares every layout that fits them as cards (a drawing of data and protection disks, usable space, how many disks may fail, reading and writing, what the layout is good for and what cannot change later), recommends one for the number of disks (mirror for two, RAID-Z1 for three to five, RAID-Z2 from six), asks whether to encrypt (only possible when the pool is created; encryption itself comes with the key vault) and shows the exact commands before it creates the pool. New pools get the Pithyx dataset layout below `<pool>/pithyx` (shares, homes, apps, system). Each pool card lists its datasets and can create share datasets, add and remove hot spares, take devices offline and online, replace a device (a new disk is never used on its own: its serial number is always typed) and destroy the pool after its name is typed. A disk that comes back is rebuilt by ZFS on its own; the card shows the rebuild.
- `POST /api/storage/plans` plans a destructive storage action (`pool.create`, `pool.destroy`, `pool.replace`, `pool.spare.add`, `pool.spare.remove`, `pool.offline`, `pool.online`, `dataset.create`) and returns the exact commands with a plan id; `POST /api/storage/plans/{planId}/run` runs it once, as shown, as a job, for the administrator who saw it and within 10 minutes. It replaces `POST /api/storage/pools/preview`. New error codes `storage.dataset.exists`, `storage.dataset.name_invalid`, `storage.encryption.unavailable`, `storage.plan.action_invalid`, `storage.plan.not_found`, `storage.pool.encryption_required`, `storage.pool.name_mismatch`, `storage.pool.not_found` and `storage.vdev.not_found`. Vdevs carry their GUID (`vdevGuid`).
- Storage settings (step 7): a Settings app for administrators (start menu, and a desktop shortcut for new administrators) with a Storage page that shows the pools live (layout, health, fill level, last scrub or rebuild) and every disk with the disk guard's verdict, plus a pool preview that lists the exact commands and runs nothing. `GET /api/storage/pools`, `GET /api/storage/disks`, `POST /api/storage/pools/preview` and the topic `storage/pools`, administrators only. The daemon reads pools from OpenZFS 2.3 as JSON and refreshes them on every `zpool events` event, without polling.
- Disk guard: the system disk (holding `/`, `/boot`, `/boot/efi`, swap or `/var/lib/pithyx`, also through LVM, crypt, md or a root pool) is always refused, disks of imported pools and mounted disks too; on a dev machine (`/etc/pithyx/environment`) only the disks in `/etc/pithyx/test-disks` can be used; a disk with partitions or signatures (`wipefs --no-act`, `blkid -p`) needs its serial typed. Command plans are checked by the guard again right before every command. New error codes `storage.command.failed`, `storage.disk.not_found`, `storage.disk.refused`, `storage.plan.expired`, `storage.plan.stale`, `storage.pool.disk_count`, `storage.pool.layout_invalid`, `storage.pool.name_invalid` and `storage.pool.name_taken`.
- `@pithyx/sdk/host`: `extensions` in `serveApp` for host-only methods the desktop gives its own core apps; they are not in `capabilities` and cannot shadow a public method.
- Dev VM: `tools/dev-vm/pithyx-dev.service` and `install-dev-daemon.sh` run the daemon as root in real mode on port 7484. A `storage` CI job runs ZFS integration tests on file vdevs and loop devices when storage code changes.
- `tools/dev-vm/start.sh` starts a test session: it builds the desktop and runs the daemon on port 7484 with its own database in `~/.cache/pithyx-run` (`--reset`, `--real`, `--no-build`).
- Files app: browse the shares you can use in a virtualized list that loads page by page, sorted on the server by name, size or date, with folders you visited shown at once and kept up to date while they are open (changes from other sessions and from the file system appear live). Select with click, Ctrl, Shift or the keyboard; Ctrl+A selects the whole folder without loading it. Create folders and rename in place, upload with the button or by dropping files, download with a double click, copy, cut and paste (also between Files windows), drag onto folders (Ctrl or Alt copies), and delete into the share's recycle bin or, after asking, for good. A name that exists already asks once whether to skip, replace or keep both. Uploads and operations show their progress in the status bar and can be cancelled. Each share has its recycle bin in the sidebar, with restore, delete for good and empty. The window remembers its folder across reloads, and narrow windows show the sidebar as a sheet. New users get a Files shortcut on the desktop.
- `@pithyx/sdk` file manager API: `files.shares`, `files.list` (with `sort`, `order` and `total`), `files.watch` and `files.unwatch` with the `folderChanged` event, `files.upload` with `uploadProgress`, `files.download`, `files.createFolder`, `files.rename`, `files.run` for copy, move and delete as jobs with the `jobChanged` event and `jobs.cancel`, `trash.list`, `trash.restore`, `trash.delete`, `trash.empty`, and `ui.showError` for the desktop's error dialog. A whole folder is named as `{ all: true, except }` instead of every name; `POST /api/files/operations` takes it as `allIn`.
- `@pithyx/sdk` draft (not frozen): app manifest types, the protocol between apps and the desktop (handshake, calls, lifecycle events, `beforeClose` and `beforeLogout`), `connect()` for sandboxed apps, an in-process and a MessagePort transport with the same behavior, RFC 9457 problems passed through as `PithyxError`, public `--pithyx-*` theme variables (20 semantic names, including hover, selected and raised surfaces), and the desktop half as `@pithyx/sdk/host`. A sample app (`apps/demo`, plain TypeScript) runs in a sandboxed window. Files under `/apps/` are served with `Access-Control-Allow-Origin: *` so sandboxed pages can load their scripts. The draft follows the SDK guardrails in `TODO.md`: permissions declared in the manifest and checked by the daemon (`app.permission.denied`, `app.storage.too_large`), elevated backend rights named one by one (`docker.socket`, `host.network`, `host.pid`, `device:<path>`, `capability:<name>`, `host.full`), named storage requests mapped to shares, a file API with opaque file handles instead of paths, `density` in the theme, the user's language as `lang` on the app root, `Intl` formatters (`app.format`) and an optional ICU helper (`@pithyx/sdk/i18n`); `session.restore()` is async.
- Leaner CI: a new push to a pull request cancels its running CI, pull requests that change only Markdown or `website/` skip the builds and E2E, daemon tests run only for daemon-side changes, and the run on `dev` after a merge skips the performance budgets (`PITHYX_SKIP_BUDGETS=1`).
- Git worktrees for parallel work live under `.worktrees/` (gitignored, skipped by ESLint) and are removed once their PR is merged.
- Shares (before M3's pools and SMB): an administrator registers an existing folder as a share (`POST /api/shares`; no system folders, no symlinks, no overlap with another share) and grants users read or read-write access (`PUT /api/shares/{id}/access/{userId}`); `GET /api/shares` lists the shares a user can use. Migration 0005 adds `shares` and `share_access`. Simulation mode seeds a share "Shared".
- File service over shares (`/api/files/{shareId}/...`): folder pages in natural order with keyset cursors that stay valid while the folder changes, size and date orders, range downloads with ETag and `Content-Security-Policy: sandbox` (attachments unless `inline=true`), streamed uploads that appear only when complete and never replace an existing name unless asked, new folders and renames. Copy, move and delete run as jobs (`POST /api/files/operations`) with progress and conflict choices (fail, skip, overwrite, rename); copies run in the kernel (`copy_file_range`). Every path is opened below the share root by the kernel, so neither `..` nor a symlink leads outside a share. New error codes under `fs.*`.
- Recycle bin per share: deleting moves files and folders to the share's hidden recycle bin (`GET /api/files/{shareId}/trash`), from where they can be restored to their original place (`POST .../trash/restore`, missing folders are recreated, taken names get "name (2)"), deleted for good one by one (`POST .../trash/delete`) or all at once (`POST .../trash/empty`). Administrators set how long a share keeps deleted items (`PUT /api/shares/{id}/trash`, default 30 days, 0 until emptied); an hourly job removes expired items. Deleting without the bin needs `permanent: true`. Migration 0007 adds `trash_items`. New error code `fs.trash.retention_invalid`.
- Live folder changes: the topic `files/<share>/<folder>` of a listed folder sends changed and removed entries while it is subscribed, from inotify without polling and without events for reads.
- Background jobs for long operations (the file service's copy, move and delete will use them): persisted in SQLite (migration 0006 adds `jobs`), at most two running at once in the order they were queued, with progress, result and error code. `GET /api/jobs` lists the user's recent jobs, `GET /api/jobs/{id}` reads one (administrators can read every job) and `POST /api/jobs/{id}/cancel` cancels a queued or running job. The topic `jobs/{id}` pushes every change to the job's owner and administrators, at most every 250 ms. Jobs that were queued or running when the daemon stopped become `interrupted` and are never resumed; finished jobs are deleted after 7 days. New error code `jobs.job.not_found`.
- `pnpm check:bundle` holds two bundle budgets (gzip) against `tools/checks/bundle-budget.json`: the sign-in bundle (everything `index.html` loads before the first render, at most 200 KB) and the desktop bundle that signing in adds. Each fails the build when it grows more than 5 percent over its baseline. It runs in CI after the build.
- E2E tests run with reduced motion and cover the window manager at phone, tablet, laptop and ultrawide sizes, with mouse, touch and keyboard. They check WCAG 2.2 AA with axe and fail on uncaught page errors.
- Performance budgets as an E2E test against the production build on Chrome's "Fast 4G" with a four times slower CPU (median of five fresh sign-ins; a median of fewer than three valid runs fails the budget): sign-in screen usable within 1.5 s from a cold cache, visible feedback within 100 ms of clicking "Sign in", desktop usable within 1 s of the click without the Argon2 time, and within 500 ms of a reload. `node tools/perf/measure.ts --url <address>` prints the same measurements, unthrottled and throttled, for any running daemon, as medians of `--runs` runs (default 5, at least 3).
- Layout memory: the desktop saves its windows, stacking order, focus, taskbar position and screen size per user and device with `PUT /api/desktop/layout` (debounced by one second, flushed before sign-out, and as a keepalive request when the tab is hidden or closed) and restores them after sign-in or a reload. Only the visible, focused tab saves. Every save names the version it builds on (`If-Match`, returned as `ETag` and in `GET /api/desktop` as `layoutVersion`); a save from another tab in between is answered with 412 `desktop.layout.conflict`, and the tab in use saves its layout on top. Windows of apps that are gone are skipped with a notice. Windows are shown within the current screen but keep their saved position, so they return to it when the screen grows again. Signing out forgets every window, size and notice of the user in that tab.
- A long-lived HttpOnly, SameSite=Strict cookie `pithyx_device` identifies each browser profile, `Secure` on HTTPS; it is set when a session starts and, for a browser that lost it, with its next save. "Get desktop from ..." in the account menu lists the user's other devices (browser and system from the User-Agent, screen size, windows, last use) and copies a layout to this device (`GET /api/desktop`, `GET /api/desktop/devices`, `POST /api/desktop/layout/copy`, which returns the layout with its new version).
- Closing a window on a large screen remembers its size for the app's next window, for the user on every device (`PUT /api/desktop/preferences/{appId}`).
- Saved layouts expire 90 days after their last save; an hourly job deletes them. Layouts hold at most 50 windows and 16 KB of app data. New error codes `desktop.layout.invalid`, `desktop.layout.too_large`, `desktop.layout.conflict` and `desktop.device.not_found`.
- Migration 0002 adds `desktop_layouts`, `window_preferences` and `desktop_items`; migration 0003 adds the layout version.
- Notification toasts for desktop events, dismissable, gone after eight seconds.
- Desktop items: app shortcuts and sticky notes on a grid, shared across the user's devices. Icons are selected with a click, Ctrl or Shift, a frame drawn over the desktop or the arrow keys, moved by dragging (a group moves together, an icon dropped on another takes the nearest free cell) or with "Move" and the arrow keys, renamed with F2 or the menu (an empty name goes back to the app's name), removed with Delete, and opened with a double click, Enter or a tap. The desktop menu (right click, long press, Shift+F10 or the menu key) creates notes and shortcuts where it was opened. Sticky notes stay under every window, move by their bar or with the arrow keys on their grip, keep up to 4000 characters on the daemon and ask before a note with text is deleted. Phones show the icons in rows of four with the notes below them. A screen too small for the arrangement shows icons in the next free cell without changing where they are stored. New users start with shortcuts to Files, Disks and About Pithyx.
- `GET` and `POST /api/desktop/items`, `PATCH` and `DELETE /api/desktop/items/{id}`: like the layout, a change sends the item's version as `If-Match: "n"` and gets the new one back as `ETag` (a new item also gets its URL as `Location`). A change made on another device in between is refused with 412 `desktop.item.conflict` and the current version in `params.version`; without `If-Match` the change is unconditional, and deleting is always unconditional and idempotent. A group move sends one request per item. The desktop saves a refused change on top, except that note text written elsewhere is never overwritten: the local text goes onto a new note next to it. At most 200 items per user. New error codes `desktop.item.conflict`, `desktop.item.invalid`, `desktop.item.limit_reached`, `desktop.item.not_found` and `desktop.note.too_long`. Migration 0004 puts desktop items on a grid with a version and gives existing users the default shortcuts.
- Phones: apps run full screen; the app switcher in the taskbar shows every open app (tap to switch, close one or all), a horizontal swipe along the taskbar switches to the next or previous app, and the Android back gesture or browser back returns to the home screen without leaving the desktop, however many apps are open.
- Tablets: windows open maximized; snapping from the window menu or the keyboard puts two apps side by side.
- Windows move by their title bar and resize from every edge and corner with live content, never below the app's minimum size and always with the window buttons on the inner side and at least 48 px of free title bar inside the workspace, so it can be grabbed again. Dragging to a side edge snaps to a half (thirds on workspaces at least 2400 px wide), dragging to the top edge maximizes, a snapped or maximized window gets its free size back when pulled away, and a double click on the title bar maximizes or restores. A preview shows the snap target.
- Window menu behind the app icon in the title bar (restore, move, size, minimize, maximize, snap left or right, close) with a keyboard move and size mode (arrow keys, Shift for single pixels, Enter, Escape), and the shortcuts Alt+Shift+Left/Right (snap), Alt+Shift+Up (maximize), Alt+Shift+Down (restore, then minimize), Alt+Shift+PageDown/PageUp (next or previous window) and Alt+Shift+Space (window menu). The shortcuts do not apply inside text fields, where macOS uses Option+Shift with the arrow keys to select by word. When no window is left, keyboard focus moves to the start button instead of the page. Keyboard actions are announced to screen readers.
- The taskbar can sit at the bottom, top, left or right (account menu in the start menu, "Taskbar position"); phones keep it at the bottom.
- Window manager: windows open from desktop shortcuts and the start menu (search with Enter), come to the front on click, minimize and restore from the taskbar, maximize and close from the title bar. Single-instance apps focus their existing window. Windows keep their DOM position when their stacking order changes, so embedded frames never reload.
- Core apps "Disks" (the live disk list) and "About Pithyx" (license, the attribution required by `NOTICE`, third-party notices). Apps load only when their first window opens.
- Setup and sign-in use the step 4 design: one card on the wallpaper with the server name, the setup in two steps (administrator, recovery key in two lines with copy and print), the TOTP step in the same card, a recovery code fallback, "Forgot password?" with the recovery key reset that shows the new key once, and a welcome card that stays only until the desktop's live connection is up. A language select below the card switches between automatic, English and German. Submit buttons show a spinner and their progress label ("Signing in ...") on the click and ignore further presses; after a failed submit the first invalid field gets focus and the errors are announced to screen readers.
- `tools/dev-vm/idle-check.sh` samples the running daemon from `/proc` and checks the idle budgets (below 1 percent CPU and 200 MB RSS) and reports its wakeups per second.

The sign-in screen is one small chunk with native form controls (138 KB gzip instead of 193 KB); it prefetches the desktop chunk while it is open, and the WebSocket opens while that chunk loads. A reload of a signed-in browser shows the desktop right away from a local session hint while the daemon confirms the session, and requests for the setup state and the session start from `index.html` before the scripts run.
- Requests that check a password answer with `Server-Timing: argon2;dur=<ms>`.
- After sign-in the desktop shows the wallpaper, the taskbar with clock and account menu (two-factor authentication, language, sign out, daemon status). The desktop code loads only after sign-in.

- End-to-end tests cover setup, recovery key confirmation, TOTP sign-in, the password reset with the recovery key, the language select and phone sign-in.

It runs in CI.

- Project files: AGPL-3.0 license (SDK under MIT), attribution notice, contributing guide, security policy.
- Dev VM provisioning script (`tools/dev-vm/provision.sh`) for Debian 13: toolchain, ZFS (DKMS), storage and container tools, `en_US.UTF-8` locale, environment and test disk markers.
- `tools/dev-vm/testpool.sh wipe <serial>...` clears ZFS labels and partitions from test disks after `destroy`; it refuses disks that are not test disks or belong to an imported pool.
- Shell scripts are checked with ShellCheck in the pre-commit hook and CI.
- Daemon command runner (`ICommandRunner`) that always runs tools with `LC_ALL=C.UTF-8`, logs every call and kills commands on timeout.
- Simulation mode (`PITHYX_SIMULATE=1`): the daemon answers commands from recorded fixtures (`tools/fixtures/record.sh`). `GET /api/health` reports `mode` (`real` or `simulated`).
- Desktop shows the daemon connection status, translated into English and German (i18next with ICU, TanStack Query).
- Vite dev server proxies `/api` and `/ws` to the daemon (`PITHYX_DAEMON_URL`), and `pnpm dev` starts the desktop.
- The pre-commit hook caches ESLint and Prettier results and lints staged files without type information, so a typical commit stays under 5 s. `pnpm lint` and CI run the full type-checked rules.
- README section "Development": simulation and dev VM workflows, test pools, common problems.
- Daemon logs are structured JSON (Serilog) on stdout and in a size-capped rotating file. Every entry carries the request id; passwords, tokens, cookies and other secrets are masked, including sensitive command arguments.
- Every API response carries an `X-Request-Id` header (the W3C trace id; an incoming `traceparent` is honored), and external commands receive it as `TRACEPARENT`.
- API errors are RFC 9457 problem details with a stable `code`, `params`, an English `detail` and the `requestId`. Error texts live in `i18n/{en,de}/errors.json`.
- OpenAPI document at `/api/openapi.json` and, in development, an API reference at `/api/docs`.
- Generated TypeScript API client (`@pithyx/api-client`) with the error code union, CSRF header middleware and `PithyxApiError`; `pnpm generate` and a drift check keep it in sync with the daemon.
- Problem details for bare status codes (404, 405) apply only under `/api/`; other paths are left to the desktop.
- Golden test (`tools/i18n/icu-golden.json`) that renders every error message and formatter edge case with the daemon's and the desktop's ICU implementation and requires identical output.
- SQLite database (WAL, foreign keys) at `/var/lib/pithyx/pithyx.db` (`PITHYX_DB`). Numbered SQL migrations run at startup, each in its own transaction, after a `VACUUM INTO` backup of an existing database; the daemon refuses to start if a migration fails or the database is newer than the daemon.
- First-run setup (`/api/setup`) creates the administrator and a recovery key that is shown once. User names must be valid Linux user names and are stored in lower case; an optional display name may contain any characters.
- Login with Argon2id password hashes (libsodium), session cookies (HttpOnly, SameSite=Strict, 7 days idle, 30 days at most), logout and `/api/auth/session`.
- Optional TOTP two-factor authentication with ten single-use recovery codes, as a second login step.
- Password reset only with the recovery key; it ends all sessions, turns TOTP off and issues a new recovery key.
- New passwords are checked against an offline list of the most used passwords from breach data (`auth.password.too_common`); there are no composition rules.
- German texts use the informal "du".
- Failed login, TOTP and recovery attempts are rate limited (`auth.rate.limited` with `Retry-After`).
- State-changing API requests require the `X-Pithyx-Request: 1` header (CSRF protection); the generated client sends it.
- Every API endpoint requires a session unless it is explicitly public.
- WebSocket at `/ws` for server-pushed data: `sub`/`unsub` with MQTT-style `+` and `#` wildcards, `ack`, `snap` (current state) and `event` (changes) messages with request ids, per-topic permission checks and throttling. Only same-origin connections with a valid session are accepted; logout and password reset close them with code 4401.
- Fixed table of WebSocket close codes shared by daemon and client: 1001 daemon restart and 1008 client too slow (reconnect with backoff and restore subscriptions), 4401 session ended (go to login, also when the session expires while connected) and 4403 origin or permission rejected (no reconnect). Rejections are sent as close codes after the handshake so browsers can tell them from network errors. An open WebSocket keeps its session alive up to the absolute 30-day limit.
- Topic `system/info` (host name, uptime, load, CPU, memory from `/proc`), published once per second only while someone is subscribed.
- Desktop walking skeleton: first-run setup with the one-time recovery key (copy and print), sign-in with an optional TOTP step or recovery code, a desktop with a live "Disks" window, two-factor setup with a QR code, sign-out, a language switch (automatic, English, German) and an error dialog that shows the translated message and the request id with a copy button.
- The desktop keeps one WebSocket per tab, restores subscriptions after reconnecting with backoff and returns to the login screen when the session ends.
- The daemon serves the built desktop with `index.html` as the fallback for every path outside `/api/` and `/ws`; hashed assets are cached forever.
- End-to-end tests with Playwright (setup, disks, sign-out, wrong password with request id, German interface, TOTP), run in CI.
- Disk list: `GET /api/disks` and the topic `storage/disks` (snapshot plus added, changed and removed disks). The daemon reads `lsblk` at startup and after udev block device events, never on a request and never by polling.
- `ICommandRunner` can stream the lines of long-running commands such as `udevadm monitor`; simulation replays recorded streams.
- `tools/fixtures/record.sh` replaces serial numbers and WWNs in recorded JSON with stable pseudonyms.
- The generated client includes the WebSocket message types and the data type of every topic.

### Changed

- The start menu is now the Pithyx menu. Sign out has its own button next to the power button, which only appears for users who may restart or shut down; the account menu keeps two-factor, language, "Get desktop from ..." and the taskbar position. A tap on the Meta key (the Windows key) opens and closes the Pithyx menu.
- Signing out closes every window, so the next sign-in starts with an empty desktop; a reload still restores the windows.
- The wallpaper draws the open boxes and floating lids of the new logo.
- The word mark's drawn theta carries the real character, so "PIΘYX" can be selected and copied. About no longer says "Based on Pithyx" about Pithyx itself; forks keep that attribution as NOTICE requires.
- Inline error messages show the request id only when the daemon failed; a wrong password or an invalid name shows just the message. Error dialogs keep it.
- The search field shows focus with its rounded border instead of a square outline.
- The sign-in screen loads 15 KB less (gzip): only the active language's texts are loaded, the sign-in screen's before the first render, the desktop shell's with the desktop and each app's with the app; ICU messages are compiled at build time, so the browser no longer loads the ICU parser. Switching the language loads the new language's texts first.
- The project is now called Pithyx (pronounced "PITH-iks"). Everything carries the new name: the daemon (`Pithyx.Daemon`, assembly `pithyxd`), the npm packages (`@pithyx/*`), environment variables (`PITHYX_*`), headers (`X-Pithyx-*`), cookies (`pithyx_session`, `pithyx_device`, so everyone signs in once more), paths (`/etc/pithyx`, `/var/lib/pithyx`, `/var/log/pithyx`, `.pithyx-trash` in shares), the SDK theme variables (`--pithyx-*`), the app manifest file (`pithyx.json`) and the dev VM's test pools (`pithyxtest*`). The fixed alternative port moves from 8994 to 7484. There is no compatibility with the old name.
- New logo: an isometric pithos whose lid opens. The start button opens it on hover, focus and while the start menu is open; setup loops it, the welcome card and About open it once, and the "daemon unreachable" screen lets it breathe while retrying. Reduced motion stops every animation. The word mark reads PIΘYX; Sora has no Greek, so its theta is drawn from Sora's O with a bar as strong as the H's. About tells where the name comes from.
- Recovery keys now start with `PTHX-`. The prefix only marks the key; it is accepted with and without it.
- The account menu (two-factor authentication, language, "Get desktop from ...", taskbar position, sign out) opens from the profile at the bottom of the start menu, with the mouse, by touch or with the keyboard. The avatar next to the clock is gone from the taskbar, also on phones.
- The UI no longer assumes a secure context: everything works over plain HTTP by IP address and with the untrusted certificate of a fresh install. APIs that need a secure context go through one module with fallbacks (random ids from `crypto.getRandomValues`, copying through a temporary text field), and ESLint refuses them elsewhere. When a browser refuses to copy, the recovery key, the recovery codes or the request id are selected on the page with a hint to copy them by hand.
- The desktop loads faster and smaller: the two-factor setup dialog loads only when it is opened, and code the desktop shares with apps is built into one chunk instead of one per combination of apps (desktop bundle 91.7 KB gzip in 4 files instead of 95.9 KB in 10).
- `@pithyx/sdk`: the `app.format` formatters reuse their `Intl` objects, which makes long lists render faster, and the desktop refuses paths with `.`, `..` or empty parts before they reach the daemon (`sdk.request.invalid`).

### Fixed

- A daemon started on a database that a newer daemon wrote (schema versions it does not know) exited with code 1 and no output, and the dev unit restarted it forever. It now logs the database, the unknown versions and what to do, flushes the log, and exits with its own code 65; the unit does not restart it (`RestartPreventExitStatus=65`) and gives up after five failed starts in two minutes. Other database failures at startup are logged too.
- `tools/dev-vm/install-dev-daemon.sh` builds as the calling user also under `sudo`, so the checkout gets no root-owned files, and refuses a checkout that already has some. `--from <checkout or worktree>` runs the unit from any checkout, for example a pull request's worktree. Before stopping anything it checks the database's schema versions against the checkout (and names a worktree that knows them), lists the unit or process it would stop on port 7484 and asks (`--yes` to skip the question).

- An open WebSocket whose session expired could stay open for good when the clock passed the expiry between the session check and its timer (a clock jump, or a slow check); the next check now ends it.
- `tools/fixtures/anonymize.ts` keeps the recorded text instead of rewriting the JSON, so 64-bit ZFS GUIDs stay exact; the build-time OpenAPI run no longer reads the build machine's disks.
- The first page of a large folder no longer waits for the whole folder to be sorted: it is selected directly (about 80 ms instead of 124 to 226 ms for 100,000 entries on the dev VM), and the full order is built in the background for the pages after it. The old sort's speed depended on how the JIT had tuned shared string code for the rest of the process, which made the listing budget test flaky.
- A finished job could read as finished in memory (API) while its row still said running; the final state is now written to the database first.
- Unsubscribing from a topic acknowledged before the daemon stopped the work behind it (for example a folder watch); the work now stops first.
- Uploading and dropping files in Files failed outside a secure context (`crypto.randomUUID is not a function` when the box is reached as `http://<address>:7484`).
- Opening the account menu or the start menu's power menu can no longer sign you out by accident. A menu that opened while its button moved could sit under the pointer, and releasing the button then picked "Sign out"; "Sign out" now needs a press that starts on it. The taskbar also takes no presses while it slides in after sign-in, and it slides in only once instead of again after every move to another screen edge.
