# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Compose contract for app backends (A6, D310): `sdk/schema/compose.v1.rules.json` (in `@pithyx/sdk`) is the allowlist of the Compose subset a `backend/compose.yaml` may use; `@pithyx/cli` (`validateCompose`, also run by `pithyx validate`) and the daemon (`Apps/Compose/`) check it alike against the manifest, held together by the corpus `sdk/schema/fixtures/compose/`: images pinned by digest, no `$` interpolation, named volumes and tmpfs only, storage volumes matching `storage[].services` and `access`, elevated rights checked in both directions, per-container limits `mem_limit` and `cpus`, and safe YAML (no anchors, tags, merge keys or duplicate keys). The daemon's `ComposeRewriter` turns an accepted file into the one the box runs (project name, image ids, bind mounts in the app's dataset, app uid and share groups, the internal network, journald, `pids_limit` 1024, `oom_score_adj` 500, labels). The manifest field `backend.resources` is removed; limits belong in the Compose file. New error codes `app.compose.key_unsupported`, `app.compose.reference_unknown`, `app.compose.right_missing`, `app.compose.right_unused`, `app.compose.storage_mismatch`, `app.compose.value_invalid` and `app.compose.yaml_invalid`.
- `@pithyx/ui` (`packages/ui`, MIT): the desktop's Button, TextField, SearchField, Controls, Dialog, Menu, ContextMenu and Tooltip as a package for core and third-party apps, with `UiProvider({ locale })` and its own English and German texts (`i18n/<lang>/ui.json`), `@pithyx/ui/native` (class names and texts for native elements without React Aria) and `@pithyx/ui/tokens.css`, now the only token file (accent presets included, checked by the contrast test). The desktop compiles it from source.
- Manifest v1 contract (A2, D301, D302): `sdk/schema/manifest.v1.schema.json` describes `pithyx.json` and ships in `@pithyx/sdk` (`@pithyx/sdk/schema/manifest.v1.schema.json`, for `$schema` in the editor); the SDK's manifest types are generated from it. Compared with the draft types: app ids are the author's domain reversed plus the app name (`com.example.chat`, `org.pithyx.*` reserved), `author` (required), `license` and `homepage` are new, the icon is always `icon.svg`, the backend declares a Compose file, named `endpoints`, `health`, `root` and `elevated` instead of `image` and `port`, storage requests name the backend services that mount them, and the permission `backend` is gone (`directory.read` and `network.internet` are new). The daemon (`Apps/Manifest/`) and `@pithyx/cli` check manifests, icons and the package layout alike, held together by one fixture corpus under `sdk/schema/fixtures/`. New error codes `app.elevated.unsupported`, `app.icon.invalid`, `app.manifest.cron_invalid`, `app.manifest.duplicate`, `app.manifest.id_invalid`, `app.manifest.id_reserved`, `app.manifest.invalid_json`, `app.manifest.reference_unknown`, `app.manifest.schema_violation`, `app.manifest.sdk_invalid`, `app.manifest.version_unsupported`, `app.manifest.window_size_invalid` and `app.package.layout_invalid`.
- `@pithyx/sdk` 1.0.0-rc.1, the SDK API v1 contract (step A4, D300 to D306): the app context carries the user's groups, administrator flag and 2FA state, `language`, the box's name and version, `visible`, `online`, `logLevel`, `backend` and `storage`; `app.backend.url`, `fetch`, `socket` and `token` reach the app's backend through the proxy routes `/apps/<id>/api/` and `/apps/<id>/api-<name>/` with a token or a one-time WebSocket ticket; `app.directory.users()` and `groups()` (only with `directory.read`), `app.log.log`, notifications with `actions`, `data` and `tag` (`notify` resolves with the notification's id), `app.setBadge`, `app.window.requestAttention`, `app.window.setDirty`, `app.contextMenu.show`, `app.clipboard.writeText` and `app.openUrl`; the events `visibilityChange`, `connectionChange`, `backendStatus`, `permissionsChange`, `storageChange`, `notificationAction` and `logLevelChange`, and the query `beforeUnload` with a reason (no veto, 2 seconds). Every `app.log` entry also goes to the browser console, and `debug` reaches the daemon only while it is switched on. Removed: `auth.token`, `beforeLogout`, `backendUnavailable`, `backendRestored` and `permissionRevoked`. New SDK codes `sdk.backend.endpoint_unknown` and `sdk.backend.unreachable`. The desktop does not serve the new methods yet (`supports()` is false, a call fails with `sdk.method.unknown`) and sends `visibilityChange` and `beforeUnload` on sign-out. The SDK version comes from `sdk/package.json`, the package has a README, repository data and correct type paths, and `tools/release/publish-sdk.sh` publishes it for the owner with npm 2FA (dist-tag `next` for release candidates, `latest` only with `--latest`) and tags `sdk-v<version>`.
- Web installer (D294, D295, D299): the ISO's live system runs the daemon as the installer. The first browser that opens `http://<address>:7484` owns the installation (the console says who); the page checks the requirements (x86-64-v2, UEFI, 4 GB memory, Secure Boot off, an internal disk of 40 GB), then asks for name and region (language, formats, time zone, console keyboard, time servers), shows the network cards, offers the system disk or a mirror of two, the administrator and a summary of the disks it erases. It partitions each disk into an ESP, a member of the system RAID1 (btrfs) and one of the swap RAID1, unpacks the live system, writes the settings and the database with the administrator, installs GRUB on every disk, shows the recovery key, restarts and opens the installed system once it answers its install id on port 80. `GET /api/installer`, `POST /api/installer/claim`, `GET /api/installer/options`, `POST /api/installer/install`, `POST /api/installer/reboot` (live system only), `GET /api/install-id`, `installer` in `GET /api/setup`. New error codes `installer.check.failed`, `installer.claim.required`, `installer.claim.taken`, `installer.disk.count`, `installer.disk.unsuitable`, `installer.erase.not_confirmed`, `installer.hostname.invalid`, `installer.install.failed`, `installer.install.running`, `installer.keyboard.invalid` and `installer.reboot.not_ready`. `image/test-install.sh` installs into a QEMU VM (one disk or a mirror) and checks the installed system.
- A box listens on port 80 as well and redirects to 7484, except `/api/install-id`.
- Dev VM: `tools/dev-vm/docker-spike.sh` checks Debian's Docker for app backends (D309) on a throwaway test pool: userns-remap with identity ranges for app uids and share gids, overlay2 on ZFS, internal networks, Compose `up --wait`, image ids after save and load, the journald fields, cgroup limits and the Engine API from .NET over the Unix socket (`tools/dev-vm/docker-engine-probe.cs`); `--record` saves the answers as fixtures in `daemon/tests/fixtures/docker/`. `tools/dev-vm/provision.sh` also installs `docker-cli`, `docker-compose`, `jq` and `nftables` and keeps Docker and containerd stopped and disabled.

- Image build (D296, D298): `image/build.sh` builds the installation ISO `image/out/pithyx-<version>-amd64.iso` without root and without Docker (mmdebstrap in unshare mode from a pinned Debian 13 snapshot, squashfs, a standalone GRUB on an appended EFI partition, xorriso); it boots with UEFI from a USB stick or as a virtual CD. The image carries the self-contained daemon, the desktop, the ZFS module for its kernel, mdadm, btrfs, Samba, OpenSSH (off), smartmontools and acl, the production unit `pithyx.service` and `/etc/pithyx/environment` set to `prod`. The console shows the ASCII logo, the box's addresses and, on the live system, a QR code of the first address, redrawn when an address changes. `image/test-boot.sh` boots the ISO in QEMU with OVMF and waits for the daemon. dev01 gets `qemu-utils`.

- Configuration backup and restore (D293): Settings > Backup and restore downloads the whole configuration (users, groups and their passwords also for SMB and SFTP, 2FA, shared folders and rights, file services, storage schedules, regional settings, the box's certificates and SSH host keys) as one `.pithyxbackup` file encrypted with a backup password (Argon2id and AES-256-GCM); files on the pools are not part of it. A restore checks the file and its password first, shows what it holds and replaces only the chosen parts (users, shared folders, storage, system, certificates); the database is copied to `pithyx.db.pre-restore-<time>.bak` first, restoring users signs everybody out, and the daemon restarts afterwards (exit code 75). `POST /api/system/backup`, `POST /api/system/backup/inspect` and `POST /api/system/backup/restore`, administrators only. New error codes `system.backup.category_missing`, `system.backup.invalid`, `system.backup.password_wrong`, `system.backup.restore_expired`, `system.backup.restore_failed`, `system.backup.restore_running`, `system.backup.too_large` and `system.backup.too_new`.
- Context menus for apps in the taskbar and the start menu: a right-click (or Shift+F10 and the context menu key) on a running app minimizes or restores it, adds it to the desktop or closes its window, and a right-click on an app in the start menu opens it or adds a shortcut to it in the first free cell of the desktop.
- WebDAV and FTP (step 12, D291, migration 0021), both off by default and switched on in Settings > File services: WebDAV at `/webdav/` of the box's address with the Pithyx user name and password, FTP with TLS (explicit FTPS on port 21, passive ports 50000 to 50099, a certificate of the box whose fingerprint Settings shows), and plain FTP without TLS only after a second switch with a warning that it is at the users' own risk (`ftpPlainAllowed`; refusing it again ends every plain session). Both need the right `protocol:webdav` or `protocol:ftp` and a shared folder that offers them (new switches in its edit dialog); they show the user's shared folders and go through the file service, so files belong to the user who wrote them and deletes land in the shared folder's recycle bin. `webDavEnabled`, `ftpEnabled`, `ftp`, `ftpPort` and `ftpFingerprint` in `/api/file-services`, `webDav` and `ftp` on shared folders.
- The permission model (step 11, D290, migration 0020): rights are grants to users and groups, and a user has the union of its own and its groups' grants; administrators have everything, and there are no deny rules. Resources: shared folders (read, read and write), the file protocols SMB, SFTP, WebDAV and FTP, the apps Files, Viewer and Demo, and the special rights administrator, desktop sign-in, SSH sign-in and restart and shut down. Settings > Users has a Rights dialog per user (showing what its groups give) and per group, the edit dialog of a shared folder sets the access of groups and users and shows what each user ends up with, and new users get the desktop sign-in, SMB and the apps unless chosen otherwise. Rights apply to the next request; a change is pushed to the desktop on the topic `session/permissions`, which closes the windows of apps the user lost, and a user without the desktop sign-in right is signed out (`auth.desktop.not_allowed`). Every API route carries the policy it needs (an endpoint matrix test checks all of them). Shared folders on a dataset get two Linux groups (`pithyx-s<id>-r`, `pithyx-s<id>-rw`) and an ACL that names only them, so a change of rights never walks the files again; an ACL changed outside Pithyx is logged and set again. Settings > File services can switch on SSH logins with a shell for users with that right (off by default; Pithyx never stops sshd). The start menu offers restart and shut down to users with that right (`POST /api/system/power`). `GET`/`PUT /api/users/{userId}/grants`, `GET`/`PUT /api/groups/{groupId}/grants`, `GET`/`PUT /api/shares/{shareId}/grants` and `GET /api/permissions/catalog` replace `GET /api/shares/{shareId}/access` and `PUT /api/shares/{shareId}/access/{userId}`; the users API carries `rights` and `protocols` instead of `smb` and `sftp`, and `isAdmin` is no longer set there. New error codes `auth.desktop.not_allowed` and `permissions.grant.invalid`.
- Groups (step 10, D289, migration 0019): Settings > Users lists the groups below the users and creates, renames, describes and deletes them and sets their members; the user dialogs set a user's groups as well. `GET`/`POST /api/groups`, `PATCH`/`DELETE /api/groups/{groupId}`, `groupIds` in the users API, administrators only. Every group is a Linux group with a gid from 30000 to 39999 that is never given out again; the daemon brings `/etc/group` in line with `groupadd`, `groupmod`, `gpasswd` and `groupdel` at start and after every change, only for groups in that range, and refuses names of system groups. The built-in group `users` (the system group every Pithyx account already has) holds every user and cannot be changed. New error codes `users.gid.exhausted`, `users.group.builtin`, `users.group.description_invalid`, `users.group.exists`, `users.group.name_invalid`, `users.group.name_reserved`, `users.group.not_found` and `users.group.refused`.
- SMB and SFTP (step 12 without NFS, D287 and D288): Settings > File services switches each on or off, sets the SMB workgroup and shows how each service is doing (`GET`/`PUT /api/file-services`, migration 0017; SMB is on and SFTP off by default). `smb.conf` is generated from the database with a "Managed by pithyx" header, checked with `testparm` before it replaces the old file (the distribution's file is kept once as `smb.conf.pre-pithyx`), and the owner's own settings go into `/etc/samba/pithyx.local.conf`, which Pithyx never writes. SMB is SMB 3 only with signing required, no guests and no NetBIOS; ACL editing over SMB is off, so rights change only in Pithyx; each shared folder can require encryption, macOS gets `fruit`, restore points show as "Previous versions", and only the users with access see a share. Files deleted over SMB go into the shared folder's recycle bin with a row per file, so Files lists and restores them. SFTP uses `internal-sftp` in a chroot below `/run/pithyx/sftp/<user>` that shows only the user's shared folders (bind mounts), with a password, without a shell or forwarding; every other Pithyx account cannot sign in over SSH at all (sshd drop-in `50-pithyx.conf`, checked with `sshd -t`). Rights per user (`smb`, `sftp` in the users API; administrators have both) and per shared folder (`smb`, `sftp`, `smbEncrypt` in `PATCH /api/shares/{shareId}`). The Linux and Samba accounts get the password at setup, sign-in, a new user, an administrator's reset and recovery; the Users page marks users who still need to sign in once. Used space follows writes over SMB (Samba's audit log) and SFTP (while a session is open). New error codes `fileservices.service.unavailable` and `fileservices.workgroup.invalid`; a shared folder can no longer be named after a Samba section (`global`, `printers`, `homes`, `print$`, `ipc$`).
- Users can be deactivated (`PATCH /api/users/{userId}` with `disabled`, and a button on the Users page): a deactivated user cannot sign in (new error code `auth.account.disabled`, shown only after the right password), its sessions end, its Linux account expires and it loses its access to shared folders. Nobody deactivates themselves, and the last active administrator stays active. Migration 0016.
- Shared folders on a dataset get POSIX ACLs from their rights (D286): active administrators and users with read and write get `rwX`, users with read `r-X`, everybody else nothing, and folders pass the same entries on to what is created in them. The ACL is set with `setfacl` (package `acl`) whenever the shares, their rights or the users change, and only for shares whose rights changed.
- Settings is an overview of tiles in three categories (System, Files and sharing, Users) with a search; a tile opens its page and "All settings" goes back. New pages: Info Center (Pithyx version and commit, operating system, kernel, machine, processor, memory, host name, uptime; `GET /api/system/overview`), Network (every interface with its addresses, DHCP or static, gateway and name servers, read only until changes come with the 60 second confirmation timer; `GET /api/system/network`), Regional settings (system language, formats, time zone and time servers; `GET`/`PUT /api/system/region`, `GET`/`PUT /api/system/time`), File services and Users (the page from the Linux accounts work). New error codes `system.time.apply_failed`, `system.time.server_invalid`, `system.time.servers_too_many` and `system.time.zone_invalid`.
- System language and formats (D282, migration 0014): users on "Automatic" whose browser asks for a language Pithyx does not have get the system language instead of English, and dates, times and numbers follow the chosen country for everyone (also in apps through the SDK `locale`). `GET /api/setup` carries `language` and `region` for the sign-in page.
- Restore points (D283, migration 0015): one switch per shared folder in Settings, "Daily restore points, kept 7 days", on for new shared folders and switched on for existing ones; a dialog explains what they cost and what they protect against, and "Previous versions" in Files lists them. `PUT /api/shares/{shareId}/restore-points` and `restorePoints` in `GET /api/shares/details`.
- Account menu: theme (like the system, light, dark, per device), accent color and wallpaper (the Pithyx boxes or plain), the last two saved per user for every device (D281, migration 0014, `PUT /api/desktop/appearance`, `appearance` in `GET /api/desktop`).
- A right-click in an app window no longer opens the browser's menu (Back, Reload, Inspect); text fields keep it for paste and spelling. Sandboxed apps get this from `connect()` in `@pithyx/sdk` and show their own menu by listening for `contextmenu`.
- Appearance in the account menu (start menu, your name): like the system, light or dark. The choice is kept on this device and reaches open apps at once. The name in the start menu shows a chevron, so the account menu with language and appearance is easy to find.
- CI: the E2E job runs on the runner named by the repository variable `CI_RUNNER_E2E` (a runner of its own, label `pithyx-e2e`) and falls back to `CI_RUNNER`. The daemon job leaves out the ZFS and account integration tests, the sign-off check is part of the repo job, and the E2E job builds only the daemon. The daemon's timing budget (the first page of a huge folder) runs in the E2E job instead of the daemon job.
- Users as Linux accounts (the user part of step 10): `GET`/`POST /api/users`, `PATCH /api/users/{userId}`, `PUT /api/users/{userId}/password` (ends the user's sessions) and `DELETE /api/users/{userId}`, administrators only. Every user gets a uid from 20000 to 29999 that is never given out again (migration 0013, `id_allocations`; the administrator from the setup gets 20000), the group `users` and no login shell. At start, after every change and when the pools change, the daemon brings `/etc/passwd` in line with the database with `useradd`, `usermod` and `userdel`, only for accounts in the Pithyx range; a name that a system account already has is refused, a deleted user's files and home stay. Each user gets a home dataset `<pool>/pithyx/homes/<user>` on the first pool (owner the user, mode 0700). The last administrator can neither be deleted nor lose the right, and nobody deletes themselves. The daemon warns at start when `/etc/login.defs` lets other tools allocate ids in 20000 to 49999. New error codes `users.account.refused`, `users.uid.exhausted`, `users.user.exists`, `users.user.last_admin`, `users.user.not_found` and `users.user.self`. A standalone Users page (create, edit, new password with the strength meter, delete after typing the name) waits for the new Settings shell.
- Files, folders, copies and restored items the daemon creates belong to the requesting user's Linux account (`fchown`/`fchownat`, group `users`) when the daemon runs as root, so SMB, NFS and SFTP see the right owner (release blocker D89).
- Uploads and downloads of every app show in the taskbar while they run: a button with the overall progress opens a list with a progress bar, the transferred and total size, the speed, the time left and a cancel button per transfer. Several transfers run at once; a failed one stays in the list until it is removed. Downloads above 4 GB go to the browser's own download. The SDK code `sdk.transfer.cancelled` reports an upload the user cancelled.
- Log Center (administrators only, its own chunk): the logs of the daemon, the kernel and the relevant system services (Samba, SSH, ZFS, network, time, Docker; followed with one `journalctl --follow`) and of every app, newest first, filtered by level, source and time range, with a search over messages, fields and exact request ids, a details pane and export as text or JSON lines. The current logs live in `logs.db` next to the daemon's log files on the system disk, written in batches, capped together at 4 GB and 30 days by default, so they are there without a pool and during boot. An optional archive on a pool (`<pool>/.pithyx/system/logs/archive.db`, the first pool by default) keeps entries longer; it is filled about once a day and before the current logs drop entries, and both are shown together. `GET /api/logs`, `GET /api/logs/sources`, `GET /api/logs/export`, `GET`/`PUT /api/logs/settings` and the error codes `logs.app.invalid`, `logs.archive.pool_unavailable`, `logs.batch.too_large`, `logs.query.invalid` and `logs.settings.invalid`. The daemon's request log stays in its log files only.
- `@pithyx/sdk`: `app.log.debug`, `info`, `warn` and `error` write to the app's log in the Log Center (source `app/<id>`, with the signed-in user). Calls return at once and never throw; the SDK batches them into the new method `log.write`, and the daemon keeps each app within 200 entries at once and 20 a second (`POST /api/apps/{app}/logs`), reporting what it dropped once a minute.
- Notification center (Release 0.1): the daemon keeps every user's notifications (at most 200, none older than 30 days; migration 0012) and sends them on the per-user topic `notifications`. A job that ends notifies its owner (done, failed with the error, cancelled, or interrupted by a restart); a storage alert that appears or gets more severe notifies every administrator once, also across restarts, and its clearing says so; SDK `notify` goes to the daemon and lands in the history, and the core apps may use it too. The bell panel shows the user's running jobs with progress and cancel (new per-user topic `jobs`), the storage alerts (still mutable, not deletable) and the history with dismiss and "Clear all"; opening it marks everything read. Every new notification shows as a toast with the icon of its app, and the badge counts unread notifications and unmuted alerts. `GET /api/notifications`, `POST /api/notifications/read`, `DELETE /api/notifications/{id}`, `DELETE /api/notifications`, `POST /api/notifications/app`, owner-only; new error codes `notifications.message.invalid` and `notifications.notification.not_found`.
- CI: the E2E suite, the performance gate and the design checks run only with the label `e2e` on a pull request, a manual workflow run, or for `master`; every pull request still runs the repository, DCO, daemon and frontend checks it needs.
- The daemon refuses to start with exit code 78 when it would create a second installation in `.pithyx-dev/` on a Pithyx machine (a machine with `/etc/pithyx/environment`, such as the dev VM).
- Dev VM: `tools/dev-vm/reset-dev-db.sh` resets the database of `pithyx-dev.service`, and `tools/dev-vm/seed-dev-accounts.sh` sets up the owner account from `~/.config/pithyx-dev/owner.env` and the test accounts `e2e-admin` and `e2e-user` after every reset and deploy.

- A live strength meter below every new password (setup and the recovery reset; user management and the password change use the same field): weak, medium or strong with the most important reason (too short, too well known, only well-known words, repeated characters or blocks, keyboard or alphabet sequences, or simply a few characters more) and a tip that long passphrases are easier to remember. Weak passwords are allowed with a warning. The estimate is a small function of our own over the 5,000 most used passwords and 3,000 most used words from breach data, loaded only when a form that sets a password opens.
- A development build of the daemon listens on `PITHYX_DEV_PORT` instead of 7484 when it is set, and the E2E suite runs on `PITHYX_E2E_PORT`, so tests and a second daemon run next to dev01's dev unit. Production builds always use 7484.
- Shared folders in Settings (the base of step 12, before SMB, NFS and SFTP): the Settings app has a navigation and its first page, Shared folders, with every share's pool, used and free space or quota, description and rights. "Create shared folder" makes the share its own dataset `<pool>/pithyx/shares/<name>` (mounted at `/<pool>/<name>`) through a command plan: the dataset name comes from the share name (lower case, accents dropped, other characters as `-`, at most 64 characters) and is shown with the exact command before it runs. "Edit" changes the name users see and the description, and sets every user's access (none, read, read and write) at once. "Delete" needs the name typed and a choice: keep the data (the dataset and its files stay, visible in Storage) or delete it for good (`zfs destroy`, `-r` only with every snapshot listed, never `-R` or `-f`); plain folder shares can only be kept. `GET /api/shares/details`, `PATCH /api/shares/{shareId}`, `GET /api/shares/{shareId}/access` and `POST /api/shares/plans` (`share.create`, `share.delete`, run with `POST /api/storage/plans/{planId}/run`), administrators only. Migration 0011 adds `description` and `dataset` to `shares`; a renamed share dataset takes its share along. New error codes `fs.share.data_choice_required`, `fs.share.dataset_name_invalid`, `fs.share.description_invalid`, `fs.share.folder_dev_only`, `fs.share.name_mismatch`, `fs.share.name_reserved`, `fs.share.no_dataset`, `fs.share.path_taken` and `fs.share.pool_not_prepared`.
- The topic `shares/list` tells every signed-in user that their list of usable shares may have changed; it carries only a revision, never a share's name. `@pithyx/sdk` raises it as the event `sharesChanged` for apps with `files.shares` (the host drops it for other apps), and Files shows new shares at once and leaves a share that went away.
- Storage app for administrators (step 8): the Disks app became Storage, with its own icon, in the Pithyx menu and on administrators' desktops, loaded as its own chunk. Sections: pools (the pool wizard, repair and maintenance through plans), disks (the guard's verdict and SMART health in one table), datasets and volumes (space, limit, compression and folder of every dataset), snapshots, and health and maintenance (alerts, scrubs and self-tests). Settings holds system settings only and points to Storage. Migration 0010 turns administrators' Disks shortcuts into Storage shortcuts and removes the Disks shortcut of other users; new administrators start with Files, Storage, Settings and About, other users with Files and About.
- Dataset actions in the Storage app: each dataset row has Limits (quota, reservation, compression and record size, with the current values; an empty size is no limit, and only what changed is sent), Rename and Delete (after typing the full name, listing every dataset and snapshot that goes), where the daemon allows them, and pools Pithyx set up have Create volume (size, sparse or not). Every action shows its exact commands first and runs as a job. The pool root now takes a compression setting too (`dataset.set`), like the Pithyx layout datasets.
- Datasets and volumes through command plans (step 8): `dataset.rename` (below the same parent; share folders and snapshot schedules follow), `dataset.set` (quota, reservation, compression, record size in one `zfs set`), `dataset.destroy` (after typing the full name, listing every child and snapshot that goes, `-r` only then, never `-R` or `-f`) and `volume.create` (zvols below `<pool>/pithyx/volumes`, sparse or thick, 16 KiB blocks). The pool root, the Pithyx layout datasets and homes, apps and system data are never renamed or destroyed; datasets that hold a share or a held snapshot are not destroyed. - Deleting a user cancels the user's queued and running jobs and drops its jobs and notifications from the daemon's memory. Users created in user management take their uid as their id, so a user id is never given out again and a new user can never see what belonged to a deleted one.

- Deleting a shared folder, and every other share or dataset plan, no longer ends in the SDK's request timeout when ZFS does not answer: a plan waits at most 10 seconds for the ZFS state it reads and then answers `storage.zfs.unavailable`, which says that a pool may be waiting for missing disks. - Used and free space of pools, shared folders and datasets, and the fill level alerts at 80 and 90 percent, follow uploads and file jobs: writes raise no pool event, so the file service tells the daemon (an upload, a copy, move, delete, restore or recycle bin job that ended, the recycle bin's cleanup), which reads the pools again 6 seconds after the last write, once ZFS has synced them, and at least every 30 seconds during a long run of writes. Writes over SMB or SFTP show with the next pool read.
- A disk pulled out of a running box degrades its pool at once: without ZED, ZFS notices a missing disk only on its next write, so the daemon now derives the pools' health from the connected disks as well (a leaf whose device is gone is `REMOVED` with `missing: true` and the serial it was last seen with; its mirror, RAID-Z and pool degrade as ZFS would), raises the alerts `storage.alert.diskMissing` and, for a pool whose I/O ZFS suspended (read from `/proc/spl/kstat/zfs/<pool>/state`, which never blocks), `storage.alert.poolSuspended`.
