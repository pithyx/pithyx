# Decisions

Architecture and process decisions of Pithyx: the choice, the alternatives and why. Each has a number `Dnnn` that code comments, commits and the docs refer to. Decisions up to D268 are recorded in the pull requests that made them; from D269 on they are listed here, in number order.

A new decision takes the next free number, is added at the end in the same pull request that makes it, and names its weight (low, medium, high), the date and who decided. A decision that changes an earlier one says so; the earlier entry stays as it was.

Next free number: D405.

- **D269** (low, 2026-09-30) CI runs on the runner named by the repository variable `CI_RUNNER` (`runs-on: ${{ vars.CI_RUNNER || 'ubuntu-latest' }}`), the owner's self-hosted runner without Docker and root. The `storage` job (real ZFS, `modprobe`, `sudo`) left GitHub CI; its tests run on the dev VM through `tools/dev-vm/integration.sh`, with the sparse files in `/dev/shm` so the host's worn SSD sees no writes. Update of the same day, by the owner: the self-hosted runner (label `pithyx-ci`) is the CI; the dev VM has too few resources for the performance gate and E2E and runs only build and test checks before a push and the ZFS integration tests. `tools/ci-local.sh` stays as an emergency fallback for a runner that cannot run a job at all, never as a replacement for a red job. The pnpm jobs failed on the runner because pnpm 12 needs `libatomic.so.1`; the owner installs `libatomic1` there, and the workflows get no workaround. Alternatives: keep the storage job on GitHub-hosted runners (blocked by the billing lock and gone for good with a private runner) or give the runner root (rejected: a CI job must never be able to touch the host's disks).
- **D270** (medium, 2026-09-30) A disk that returns after it was pulled is reopened (`zpool online`) before a suspended pool is resumed (`zpool clear`), and both give up after 30 seconds so the pool reads go on. Seen on the dev VM with `scsi_debug` disks: while ZFS still holds the deleted device, `zpool clear` waits in the kernel, and behind it `zpool destroy`, `zpool list` and even writes to ZFS module parameters wait until a reboot. The disk pull tests therefore run only with `integration.sh --disk-pulls` on a freshly booted dev VM. Alternatives: run them in every integration run (rejected: one bad run blocks ZFS on the dev VM until a reboot) or drop them (rejected: they are the only automated check of the owner's procedure). Open: why the transaction group waits although the disk is back; to be traced on a fresh boot.
- **D271** (low, 2026-09-30) Downloads run through `fetch` into a Blob so the taskbar can show their progress and cancel them; the file is saved from the Blob under its name. Above 4 GB (by `Content-Length`) the browser's own download takes over, because browsers keep large Blobs on disk only up to a limit. Alternatives: a service worker that streams to disk (needs a secure context, which the untrusted default is not) or the File System Access API (secure context and Chromium only).
- **D272** (low, 2026-09-30) After loading and reloading, nothing has focus; the start button takes the focus only when the last window closes or minimizes. Keyboard users reach it with Tab. Alternative: keep focusing it on load (rejected by the owner: a focused button after every reload looks like a stuck state).
- **D273** (low, 2026-09-30) the dev VM has one dev instance: `pithyx-dev.service` on port 7484 with the one database `/var/lib/pithyx/pithyx.db`, always running dev from the main checkout (`install-dev-daemon.sh` fast-forwards it to `origin/dev`; `--from` is gone) and deployed after every merge. The database is reset only with `tools/dev-vm/reset-dev-db.sh`, and `tools/dev-vm/seed-dev-accounts.sh` sets up the owner account (credentials and recovery key in `~/.config/pithyx-dev/owner.env`, mode 600) and the test accounts `e2e-admin` and `e2e-user` (`e2e.env`, once the users API exists) after every reset and deploy. The owner account is never changed. A fresh state or an unmerged branch runs on a short-lived instance on port 7485 in a `mktemp -d` directory (`tools/dev-vm/start.sh`). Alternatives: switching the unit between databases or checkouts (rejected: the owner could not sign in or watch while an agent worked) or a second permanent instance (rejected: two states to keep apart on a 4-core VM).
- **D274** (low, 2026-09-30) In dev environments (dev VMs, CI) the agent needs no permission for anything: packages, services, configuration, kernel modules, reboots, pools and arrays, databases, every file including `CLAUDE.md`. The hard limits are no push or merge to `master`, no delete, force-push or rewrite of `origin/master` and `origin/dev`, and on the dev VM `sda`, other machines, the runner server and secrets. `.claude/settings.json` keeps only deny rules for pushes to `master` and force-pushes or deletes of `dev`; the owner's `autoMode` settings on the dev VM tell the auto-mode classifier the same. Alternatives: ask before every system change (rejected by the owner: it blocks the work and saves nothing on a throwaway VM) or keep the raw disk command denies (rejected: `testpool.sh` and the classifier cover the test disk limit, and scsi_debug disks need `wipefs` and `zpool create`).
- **D275** (low, 2026-09-30) `tools/ci-local.sh` is removed, by the owner: the dev VM is too weak to build and test, so builds, lint, typecheck, unit tests, E2E and the performance gate run only on the self-hosted runner, and the agent pushes and goes on while the runner works. the dev VM keeps what needs ZFS, root or real disks (`tools/dev-vm/integration.sh`, which builds the daemon for it) and the deploy of `dev`. Same day: `docs/dev/HANDOFF.md` is removed and its state, open work and pitfalls live in `CLAUDE.md`, so agents read one file. Alternatives: keep the script as an emergency fallback (rejected: it loaded the dev VM for results that did not count anyway) or run only the unit tests locally (rejected: the runner does the same in minutes).
- **D276** (low, 2026-09-30) `tools/dev-vm/integration.sh` stops `pithyx-dev.service` for the test run and always starts it again (owner's choice). The dev daemon manages every pool it sees: on the dev VM it created cache datasets in the throwaway test pools, held their mounts busy, and with D270 it would also reconnect and clear their pulled disks, which broke the tests and risks the ZFS wedge. Alternatives: a daemon setting that ignores pools by name prefix, set only in the dev unit (rejected: a test switch in the product) or tolerant tests (rejected: unreliable results).
- **D277** (medium, 2026-09-30) Every machine has exactly one Pithyx installation, by the owner. On the dev VM that is `pithyx-dev.service` on 7484: real mode, the database on the system disk (`/var/lib/pithyx/pithyx.db`, as on a box), the pools on the test disks. `tools/dev-vm/start.sh` (a second instance on 7485) is gone, and a daemon that would fall back to `.pithyx-dev/` (no `PITHYX_DB`) on a machine with `/etc/pithyx/environment` exits with code 78; before, a `dotnet run` from the checkout ran in real mode on the real disks with a second database in `.pithyx-dev/`. Branches are checked by the runner and `integration.sh` before the merge and on 7484 after it. Simulation stays for the unit tests and E2E on the runner, each with its own throwaway database. Alternatives: branches on 7484 before the merge (rejected: a branch migration makes the dev database unreadable for `dev`, exit code 65) or keep the second instance (rejected by the owner: two states to tell apart).
- **D278** (low, 2026-09-30) The E2E suite (with the performance gate and the design checks) runs only when asked, by the owner: the label `e2e` on a pull request, a manual workflow run, and every pull request or push to `master`. It took five to eight minutes of a single runner that runs one job at a time, for every small change. Every pull request still runs `changes`, `repo` and `dco`, and `daemon` and `frontend` when their files changed; the bundle size check stays in `frontend`. The agent adds the label for larger changes (user flows, desktop shell, sign-in, setup, SDK transport, API contract, loading path, several merges in a row) and runs it by hand on `dev` before the owner verifies on 7484. Pushes to `dev` no longer run E2E. Alternatives: E2E on every push to `dev` after the merge (rejected: it still holds the only runner slot) or split the suite into a fast smoke set (possible later; the tests share one daemon and run with one worker).
- **D279** (low, 2026-09-30) The rename from the first working title to Pithyx is finished. The GitHub repository was renamed, so old URLs and `#` references redirect to `pithyx/pithyx` with the same numbers; the repository now links only to `pithyx/pithyx` (NOTICE, README, SECURITY, the About attribution, `protect-branches.sh`, the references in this file), and the repository check allows only the `VYXTEST` serials, which are set in the hypervisor. - **D280** (low, 2026-09-30) The self-hosted CI becomes several runners on the owner's host, one job each: general runners (label `pithyx-ci`) sharing some cores, and one E2E runner (label `pithyx-e2e`) on cores of its own. The E2E job runs on `vars.CI_RUNNER_E2E` and falls back to `vars.CI_RUNNER`. One runner ran every job of every pull request one after another while most of its six cores idled; the timing budgets of the performance gate need a runner that no parallel build disturbs. Alternatives: more general runners only (rejected: parallel builds next to the E2E suite make the budgets flaky) or ephemeral runners per job (later: they need a token service to register each one). Same day, to shorten the runs: the daemon job leaves out the `StorageIntegration` tests instead of starting and skipping them, the sign-off check is a step of the repo job instead of a job of its own (three heavy jobs per pull request, one per general runner), and the E2E job builds only the daemon, not the whole solution with its tests. 2026-10-01: the daemon's timing budget (`Category=TimingBudget`) moves from the daemon job to the E2E job; on a general runner next to the frontend build its first page took 350 to 590 ms against a budget of 200 ms. 2026-10-06: the E2E job waits for the daemon job (and runs whether it passed, failed or was skipped); with the daemon tests running next to it, the pinned cores still measured a warm reload of 529 ms and a cold start of 1506 to 1514 ms against budgets of 500 and 1500 ms, while runs without that overlap passed. A pull request with daemon changes takes about ten minutes longer.
- **D281** (low, 2026-10-01) Personal look in the account menu: the theme (like the system, light, dark) stays a choice of each device in `pithyx.theme` (`theme/preference.ts`, the same module as #56), while the accent color and the wallpaper follow the user to every device, as desktop items do: SQLite `user_appearance` (migration 0014), `PUT /api/desktop/appearance`, returned by `GET /api/desktop`, cached per device in `pithyx.appearance` so the first paint matches. The wallpaper is the Pithyx boxes or plain; pictures from the user's files come later. Language and taskbar position stay where they were. Alternatives: the theme per user as well (rejected: a phone at night and a desktop by day want different schemes, and #56 already stores it per device) or everything in the browser (rejected: the desktop rules keep the wallpaper per user across devices).
- **D282** (medium, 2026-10-01) Regional settings of the box: the system language (en, de) and a region (an ISO 3166 country code, or none to follow the language), in SQLite `system_region` (migration 0014), `GET`/`PUT /api/system/region` for administrators and part of `GET /api/setup` so the sign-in page has them without another request. The system language is the fallback for "Automatic" when the browser asks for a language Pithyx does not have (before: English) and the language for messages the box renders itself later. The formats are the language with the region (`de-AT`, `en-DE`) for every `Intl` call of the desktop and the SDK context `locale`; `pickLanguage` already reduces it to the language for texts. The time zone and time servers are the host's (`timedatectl`, a timesyncd drop-in `/etc/systemd/timesyncd.conf.d/pithyx.conf`). Alternatives: a free locale tag (rejected: a select of countries is what people know), formats per user now (later, with a profile, TODO), or the system locale through `localectl` (rejected: the daemon runs every tool with `C.UTF-8`, and the desktop formats in the browser).
- **D283** (medium, 2026-10-01) Snapshots become restore points: one switch per shared folder that maps to the daily snapshot schedule of its dataset with 7 kept, `PUT /api/shares/{shareId}/restore-points` and `restorePoints` in `GET /api/shares/details`. New shared folders get it on when they are created, and migration 0015 switches it on for existing ones unless their dataset already has a daily schedule (owner's decision on 2026-09-30). "Previous versions" in Files lists the versions in them. The Snapshots section (schedules, holds, rollback, manual snapshots) leaves the Storage app; its API and code stay for a later expert view. Alternatives: keep the Snapshots section next to the switch (rejected by the owner: too much for most people) or a separate restore point store (rejected: ZFS snapshots already are one, and SMB will show them as previous versions).
- **D284** (low, 2026-10-01) The Storage app never shows the Pithyx layout and what the daemon manages (`<pool>/pithyx` with `apps`, `system`, `homes`, `shares`, `volumes`, `cache` and everything below except shared folders and volumes); the pool root, shared folders, volumes and datasets outside the layout stay. Its sections are Pools, Disks, Health and maintenance and Advanced; Advanced explains and holds volumes (create, delete), exporting and importing a pool, and the datasets table with limits, compression and names. The daemon gets the version `0.1.0-dev` (`daemon/Directory.Build.props`), which the Info Center shows with the commit. Alternatives: drop the datasets table (rejected: quotas and compression would be gone without a replacement) or hide the pool root as well (rejected: on a pool Pithyx did not create it is the user's data).
- **D285** (low, 2026-10-01) A storage command of a plan that runs into its timeout ends the job with `storage.command.timed_out` (the program with its subcommand and the minutes waited), and destroying a pool closes its dialog as soon as the job started; the pool's card says "Being deleted" and the notifications report the end. A command stuck in the kernel cannot be killed, so the timeout only decides when the user learns about it; the text says to check the disks and to restart the box if other pools stop responding. Alternatives: a code only for `zpool destroy` (rejected: export, replace and the rest can hang the same way) or a shorter timeout for destroy (rejected: it ends nothing in the kernel, and a pool with many datasets needs time to unmount them).
- **D286** (medium, 2026-10-02) Shared folders get their POSIX ACLs from `setfacl` (package `acl`), run through `ICommandRunner`, by the owner: `setfacl -R -P --set <entries>` on the share and `setfacl -R -P -d --set <entries>` for the default ACL of its folders, without following symlinks. The entries are the owner `rwX`, group and other `---`, the mask `rwX`, and one named entry per uid: active administrators and active users with `readWrite` get `rwX`, users with `read` get `r-X` (`X` gives execute to folders only, so files never become executable). The entries last set are kept in `shares.acl` (migration 0016), so a share is walked again only when its rights change, not at every start. Deactivated users (`users.disabled_at`, same migration) lose their entries, cannot sign in (`auth.account.disabled`, only after a correct password) and their Linux account expires (`usermod --expiredate 1`, read back from the expiry field of `/etc/shadow`). The image must ship `acl` (M5); `tools/dev-vm/provision.sh` installs it. Alternatives: writing `system.posix_acl_access` as raw xattrs from the daemon (rejected: a binary format of our own to maintain, and it was only chosen while the dev VM had no `setfacl`), or a native library such as libacl through P/Invoke (rejected: more code for no gain, the walk is the expensive part either way).
- **D287** (medium, 2026-10-02) SMB and SFTP for 1.0 (step 12 without NFS). SQLite holds one row `file_services` (SMB on, workgroup, SFTP off by default) and per user `smb` (on) and `sftp` (off), per shared folder `smb`, `sftp` and `smb_encrypt` (migration 0017); administrators have every protocol. Pithyx keeps only its own password hash, so the Linux account (for SFTP through PAM) and the Samba account get the password when the daemon has it in plain text: setup, sign-in if SMB or SFTP lack it, a new user, an administrator's reset and recovery, through `chpasswd` and `smbpasswd -s -a` on stdin. `smb.conf` is rendered completely from SQLite with the owner's include `/etc/samba/pithyx.local.conf` last in `[global]`, validated with `testparm` on a candidate file before it replaces the old one, and the service is reloaded only when the file changed. Every share: `valid users` and `write list` from the rights (POSIX ACLs of D286 decide on disk), `access based share enum`, `nt acl support = no`, SMB 3 with signing, `veto files` for the recycle bin, `vfs_recycle` into `.pithyx-trash/.smb/<user>` and `shadow_copy2` on the daily restore points; Samba names (`global`, `homes`, `printers`, `print$`, `ipc$`) are refused as share names. Samba deletes a file for good when it cannot create its recycle folder, so `.pithyx-trash` is root's with 0711 and `.smb` 1733, both without ACL, set on handles after every ACL walk; the daemon turns every file there into a recycle bin item with a row in the deleting user's name. Writes and deletes reach the daemon through Samba's `full_audit` in the journal the Log Center already follows (not kept in the Log Center). Alternatives: a timer that lists `.smb` (rejected: polling), inotify on every bin (rejected: the audit log also serves the used space), `smbpasswd` sync through PAM (rejected: Pithyx does not use PAM for its own sign-in).
- **D288** (medium, 2026-10-02) SFTP as D108 planned: `internal-sftp` with `ForceCommand`, a chroot per user below `/run/pithyx/sftp/<user>` (tmpfs, owned by root as sshd requires) with one bind mount per shared folder the user may use, rebuilt at start and on every change; exporting or destroying a pool takes the bind mounts with it because libzfs unmounts every mount of a dataset. sshd matches on two system groups the daemon keeps with `gpasswd -M`: `pithyx-users` (every Pithyx account) and `pithyx-sftp` (the SFTP users while SFTP is on). The drop-in `/etc/ssh/sshd_config.d/50-pithyx.conf` gives SFTP users a password login without shell, terminal or forwarding and turns every login method off for the other Pithyx accounts; it is checked with `sshd -t` and put back when the check fails. Accounts outside Pithyx are never matched, and switching SFTP off never stops sshd (that belongs to the SSH setting). `internal-sftp` cannot log from the chroot, so the used space follows SFTP by its sessions (a pool read once a minute while one is open). Alternatives: one chroot for everybody with all shares (rejected: shows names of shares a user may not use), `Match User` lists (rejected: sshd would be reloaded for every user change), `DenyGroups` (rejected: global only, the owner's accounts share the group `users`).
- **D289** (medium, 2026-10-03) Groups for 1.0 (step 10). A group's id is its gid from the D103 range 30000 to 39999, allocated in `id_allocations` like a uid and never reused (migration 0019, `groups` and `group_members`); its Linux group is kept in line by `GroupReconciler`, a pure plan like the account reconciler: `groupadd --gid`, `groupmod --new-name` for a rename (the gid stays), `gpasswd -M` with every member at once and `groupdel`, only for gids in the range, and a name that a group outside the range has is refused. Group names follow the user name rules, and `pithyx-` stays the daemon's. The built-in group `users` is the system group with gid 100 that every Pithyx account already has as its primary group: every user is a member without a row, and it can neither be renamed, deleted nor given members. This answers the question what happens to users without a group after the migration (the owner's recommended choice in the task of 2026-10-03, "a group users for everybody", taken without asking because the owner asked for autonomous work). Rights given to `users` (step 11) are never written as `g:users` on disk, because accounts outside Pithyx (the owner's on the dev VM) are in that group too. Alternatives: a Pithyx group `users` in the range with explicit members (rejected: the name belongs to the system group, so its Linux group would need another name, and a user created later would have to be added by hand), or no default group (rejected: the owner recommended one, and grants for everybody would need a group anyway).
- **D290** (high, 2026-10-03) The permission model for 1.0 (step 11). Rights are rows of `grants` (migration 0020): a subject (`user`, `group`, `app` for M4) and a resource (`share:<id>` with `read` or `readWrite`; `protocol:smb|sftp|webdav|ftp`, `app:files|viewer|demo`, `right:admin|desktopLogin|sshLogin|power` with `allow`). `PermissionResolver` is a pure function: a user gets the union of its own grants and those of its groups, the built-in group `users` included; administrators have everything; a deactivated user nothing; there are no deny rules (table and property tests). The migration turns every earlier right into the user's own grant (share access, administrator, SMB, SFTP, the desktop login for everybody, the three apps for everybody who is not an administrator), so nobody gains or loses anything, and drops `share_access`, `users.is_admin`, `users.smb` and `users.sftp`. `PermissionService` resolves on every request (cached until any right, group, membership or user changes); the session's claims carry the administrator role and the rights, and every route that needs one carries the policy `admin` or `power`, so a request without the right is refused before its body is read; an endpoint matrix test calls every endpoint as anonymous, a user without rights, a user with the power right and an administrator, and a new endpoint fails it until it is classified. A change of rights re-authorizes every open WebSocket, pushes the user's rights on the per-user topic `session/permissions` (the desktop closes windows of apps no longer allowed and hides them) and ends the connections and sessions of users without the desktop login right (`auth.desktop.not_allowed` at sign-in, only after the right password). No change may leave the box without an active administrator, also through groups. On disk (D102 on top of D286) every dataset share has two Linux groups `pithyx-s<id>-r` and `pithyx-s<id>-rw` with gids from the group range, the ACL names only them, and a change of rights changes their members (`gpasswd`) instead of walking the files; the share's folder is compared with `getfacl` at every reconcile and set again on a difference. Like any supplementary group, a new membership applies to the next login of SMB and SFTP sessions. SMB `valid users`/`write list` and the SFTP views follow the effective rights. SSH logins are a setting in File services (off by default): users with `right:sshLogin` get `/bin/bash` and the sshd group `pithyx-ssh` (password, no forwarding) and no SFTP view; Pithyx never stops sshd, so switching it off cannot lock an administrator out of the box. Restart and shut down are `POST /api/system/power` behind the `power` policy, with a confirmation in the start menu. App rights are enforced where the daemon knows the app (`POST /api/apps/{app}/logs`) and in the desktop (start menu, opening and restoring windows); until app tokens (M4) the daemon cannot tell which core app calls the file API, which the release blocker on app permissions already covers. Alternatives: per-user ACL entries expanded from groups (rejected: every change walks every file of a share), a SQL view as the resolver (rejected: the resolver must be one pure function with tests), keeping `is_admin` next to grants (rejected: two sources of truth), and a deny rule for single users (rejected by `CLAUDE.md`: union only).
- **D291** (high, 2026-10-03) WebDAV and FTP for 1.0 (step 12), `[DECISION]` taken with the owner's recommended choices and confirmed by the owner on 2026-10-03, who added plain FTP: both run inside the daemon on top of the file service and the file operations (`ProtocolFiles`), so rights (the resolver of D290 on every request and FTP command), owners (`fchownat` with the user's uid), the hidden recycle bin and deletes into it are exactly those of Files, and no second server has its own idea of them. Both are off by default (`file_services.webdav_enabled`, `ftp_enabled`, migration 0021), need the right `protocol:webdav` or `protocol:ftp` and a shared folder that offers them (`shares.webdav`, `shares.ftp`, on by default like SMB and SFTP). WebDAV answers at `/webdav/` on the daemon's own address (7484 now, 443 with the TLS step), class 1 and 2 (locks are granted, not enforced), with Basic authentication and the Pithyx password; the root lists the user's shared folders. FTP is explicit FTPS (`AUTH TLS`, `PROT P` before any data; no implicit TLS); plain FTP (no `AUTH TLS`, `PROT C`) works only while an administrator allows it with a second switch (`file_services.ftp_plain`, off by default) whose warning says it is at the users' own risk, for devices without TLS, and refusing it again closes every plain session. The FTP server is passive only (EPSV and PASV on ports 50000 to 50099; PORT and EPRT refused so the box never connects out), data connections only from the control connection's address, on port 21, with a self-signed certificate made once in `/var/lib/pithyx/tls/ftps.pfx` whose SHA-256 fingerprint Settings shows. Sign-in (`ProtocolSignIn`) checks the password hash like the desktop, with the same rate limit per address and user, and remembers a success for five minutes keyed by the stored hash, so a new password ends it at once. Users with two-factor sign-in use their password, as over SMB and SFTP. Switching FTP off closes every session. Alternatives: an external WebDAV server such as Apache or nginx with dav modules (rejected: a second rights model, owners and no recycle bin), vsftpd or ProFTPD (rejected: they delete for good, need PAM and chroots of their own, and know neither grants nor the recycle bin), plain FTP as the only mode (rejected: passwords in clear text for every client, also those that can do TLS), and a WebDAV library (rejected: none that fits the file service without wrapping every call).
- **D292** (medium, 2026-10-03, updated 2026-10-09 by D337) Changing the network for 1.0 (step 14.2, D110). Pithyx keeps what it configured as one document in SQLite (`network_config`, migration 0026: the interfaces with settings and the global part) and writes it with the pure `NetworkdConfig` as `/etc/systemd/network/10-pithyx-<name>.{network,netdev}` plus `/etc/systemd/resolved.conf.d/pithyx.conf`; cards without settings keep the image's `80-pithyx-ethernet.network` (DHCP). Then `networkctl reload` and `reconfigure` (removed or changed bonds and VLANs with `networkctl delete` first); the host name goes through `hostnamectl` and the `127.0.1.1` line of `/etc/hosts`, and Samba's `netbios name` follows it. Input is checked by the pure `NetworkValidator` before anything changes (an address with prefix in its family, a gateway inside that network, name servers as addresses, the MTU range, names that never collide with Docker's `px-*`, `docker*`, `br-*` or `veth*`, and never a box without any interface with an address); the answer names the interfaces that change and warns when the browser's own connection comes in on one of them. Every change waits 60 seconds for a confirmation (`NetworkConfirmation`, one change at a time, several fields are one change) and is rolled back to the previous files and settings when the time runs out or the administrator presses Undo; what it replaced is stored in `network_pending`, so a daemon that restarts while a change waits rolls it back at start. Both tables stay out of configuration backups: a restore must never change the network without the timer, and card names differ between machines. The Network page shows the countdown with Keep and Undo and the new address to open, to every administrator through the topic `system/network`, which follows `ip monitor` while somebody watches. Where Pithyx may change things: everything on a production box; on a development machine only the interfaces in `/etc/pithyx/test-nics` (and bonds and VLANs made of them) and never the host name, name servers or default route; in simulation everything, in memory. Alternatives: NetworkManager (rejected by D110: networkd is lighter and declarative), editing `/etc/network/interfaces` (rejected: ifupdown has no reload with rollback), a confirmation only in the browser (rejected: a closed tab would leave a wrong address in place), and a row per interface (replaced: one document is one change, and bonds and VLANs refer to each other).
- **D293** (medium, 2026-10-03) Configuration backup and restore for 1.0, `[DECISION]` with the owner on 2026-10-03: basic, always everything, encrypted with a password the administrator types (the same rules as an account password), downloaded only (nothing is kept on the box), restore only in Settings with a choice of parts.
