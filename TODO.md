# TODO

Step-by-step plan for building the Pithyx foundation. Read `CLAUDE.md` before starting and follow it at every step.

## How to use this file

- Work top to bottom. One step at a time.
- A step is finished only when every item is checked and its "Done when" criteria are met.
- `[DECISION]` means the owner must choose before you continue. Present the options with a short recommendation and stop.
- `[REVIEW]` means the owner must look at the result before you continue. Stop and ask.
- Check items off in the commit that completes them. One step usually equals one or a few commits.
- If a step turns out to be wrong or incomplete, propose a change to this file instead of silently deviating.
- Start every step in plan mode: read the relevant sections of `CLAUDE.md`, write a short plan, then implement.
- Each step and some sub-steps carry an effort level. `high` means extended thinking for design-defining work that is expensive to change later. `medium` is the default. `low` is mechanical work.

Performance and loading (owner's decisions of 2026-10-16, D354, D355):

- [ ] (N14, high) App frontends are served with `cache-control: no-cache`, without `ETag` or `Last-Modified` and without compression (Lists: 474 457 bytes instead of 145 994 with gzip), so every window downloads everything again; on the owner's device the bundle alone took 2.9 s and 4.1 s, longer than the backend's cold start (2.5 s). First find out whether Chromium caches subresources of a sandboxed iframe without `allow-same-origin` (opaque origin); if not, propose the smallest change that makes it cache without giving the frontend the desktop's origin, and ask the owner before any change to the sandbox or the CORS headers. Measure cold and warm open of Lists with Playwright before and after, label `e2e`.
- [x] (N15) Loading placeholder in every app window, drawn by the desktop (D354): icon and name, an indicator after 300 ms, until the app connected (`connect()`, or an explicit `app.ready()` if the app wants to keep it up longer); while `backendStatus` is `starting` a plain, true text (default for example "Starting Lists ..."; never a technical term). The developer may set the text (localized like `name`, in the manifest, because it shows before the app's code runs); the default comes from `i18n/`. SDK, manifest schema (additive), mock desktop, docs (events guide, manifest page) in en and de. Done: manifest `window.loading` (`text`, `untilReady`), SDK `app.window.ready()` (method `window.ready`), the placeholder in `SandboxApp` and in `pithyx dev`, at most 30 seconds; the decision logic is `loadingPhase` in `desktop/src/apps/host/rules.ts`.
- [ ] (N16) Backend start: measure first, then decide with the owner. ### Findings from the owner's test on 2026-09-29

Core bugs first, each in its own PR with a regression test:

- [x] Disk failure: a hard-removed disk only disappears from the list; there is no DEGRADED, no banner, no notification, and other pools look dead. Expected: DEGRADED at once, a banner and a persistent notification, other pools unaffected; after the disk is back, a resilver and the all-clear. Tested for real on the dev VM: remove with `echo 1 > /sys/block/<dev>/device/delete`, bring back with a SCSI rescan (`echo '- - -' > /sys/class/scsi_host/host*/scan`). - [x] Notification center and toasts do not work (no entries, no toasts): find the cause and fix it. (The daemon had no notifications at all: the bell only showed storage alerts and toasts were the desktop's own. Now the daemon keeps a history per user (jobs that end, storage alerts that appear or go away, SDK `notify`), sends it on the per-user topic `notifications` and the user's running jobs on `jobs`; the panel shows running jobs, alerts and the history, and every new notification is a toast.)
- [x] After the disks were removed and brought back, Files shows shares without files and "share not found": the mount state and the Files cache recover once the disks are back. - [x] Usage of pools, shared folders and disks does not update after uploads. Writes through the file service now trigger a pool read (D209); writes over SMB and SFTP need their own trigger when step 12 lands (see below).

#### Architecture

An app is a static frontend that the daemon serves, plus an optional backend of zero to n containers (D300). Web apps with their own port and single sign-on (Grafana and the like, `kind: "web"`) come after 1.0.

Routes, for the app `com.mueller.chat` on `https://nas.muellers.com`, whose service `server` offers port 8080 as the endpoint `api` and port 9090 as `metrics` (D303):

| What                     | URL                                                                                       | In the app                                             |
| ------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Window                   | `https://nas.muellers.com/apps/com.mueller.chat/index.html`                               | (the desktop loads it)                                 |
| REST                     | `https://nas.muellers.com/apps/com.mueller.chat/api/messages` to `server:8080/messages`   | `app.backend.fetch('/messages')`                       |
| Second endpoint          | `https://nas.muellers.com/apps/com.mueller.chat/api-metrics/stats` to `server:9090/stats` | `app.backend.fetch('/stats', { endpoint: 'metrics' })` |
| WebSocket                | `wss://nas.muellers.com/apps/com.mueller.chat/api/live?pithyx-ticket=...`                 | `app.backend.socket('/live')`                          |
| Full URL for `<img>` etc | as REST, with the token parameter                                                         | `app.backend.url('/avatar/1')`                         |

- The default endpoint is `api` at `/apps/<id>/api/`; every other endpoint `<name>` is `/apps/<id>/api-<name>/`. Container ports never appear in a URL; a new port only changes the manifest.
- Port 7484 serves the same paths. The SDK takes the box's address from its own window's URL and the app id from the handshake.

Package `<id>-<version>.pithyxapp`, a deterministic tar.gz built by `pithyx pack` (D301). The box never runs npm or a compiler.

- `pithyx.json` (the manifest) and `icon.svg`
- `frontend/`, entry `frontend/index.html`
- optional `backend/compose.yaml` and `backend/images.lock.json` (reference, manifest digest and config digest per architecture)
- optional `backend/images/<arch>/*.tar` for offline installs
- checksums, optional README and LICENSE

On the box (D301): one dataset per app `<pool>/pithyx/apps/<id>`, mounted at `/<pool>/.pithyx/apps/<id>/` with `versions/<version>`, `current`, `volumes/` and `run/`; Docker's data in `/<pool>/.pithyx/docker`. The administrator picks the app pool at the first install (setting `apps.pool`). Nothing of it lives on the system disk.

Frontend files (mandatory, D303). Every response under `/apps/<id>/` carries:

- `Content-Security-Policy: sandbox allow-scripts allow-forms; default-src 'self'; ...`, with `connect-src https:` only for apps holding `network.internet` (never script sources from a CDN);
- `X-Content-Type-Options: nosniff`;
- `Access-Control-Allow-Origin: *`.

Without `sandbox`, an `/apps/<id>/index.html` opened directly in a tab would run in the desktop's origin and could use the user's session. The icon is served from the database at `/api/apps/{id}/icon` with `Content-Security-Policy: default-src 'none'; sandbox`.

Tokens (D303):

- The desktop gets them with `POST /api/apps/{id}/tokens` (session cookie and CSRF header) and keeps them in memory: 256 bits, valid 5 minutes, bound to user, session, app and window instance.
- `host` tokens are valid for `/api/app/**`, the daemon's API for apps. The app identity comes from the token, never from the route.
- `backend` tokens are valid for the proxy, as a bearer header or `?pithyx-token=`.
- A WebSocket needs a one-time ticket, valid 30 seconds, passed as `?pithyx-ticket=`.
- A cookie alone never authenticates at the proxy.

Proxy (YARP in the daemon process, routes set at runtime, D303):

- removes `Cookie`, `Authorization`, the `pithyx-*` query parameters and every incoming `X-Pithyx-*` header;
- sets `X-Pithyx-User`, `X-Pithyx-User-Id`, `X-Pithyx-Groups`, `X-Pithyx-Admin`, `traceparent` and `X-Forwarded-Prefix`;
- answers CORS preflights for `Origin: null` itself;
- answers 503 `app.backend.unavailable` when no backend runs.

Docker (details in D309 after A1):

- From Debian (`docker.io`, `docker-cli`, `docker-compose`); it runs only while a backend app is installed and its pool is mounted.
- State and events come from the Engine API on the Unix socket, without polling. `docker compose up --wait` runs as a job through `ICommandRunner`.
- Every app gets its own internal network and its own uid from 40000 to 49999. Backends have no internet; outgoing traffic only with `network.internet`. Root in a container only when declared (`backend.root`), unprivileged through userns and shown with a warning; root on the host only through `host.full` (D304, D71).
- Container output goes through journald into the Log Center source `app/<id>` (D305).

Rules:

- ID (D302): `^[a-z][a-z0-9-]*(\.[a-z0-9][a-z0-9-]*){2,4}$`, at most 100 characters: the author's domain reversed, then the app name as the last part (`com.mueller.chat`, `io.github.schecher1.chat`, `io.gitlab.jan.chat`). `org.pithyx.*` is reserved for system apps and later the official catalog.
- Unknown fields are errors.
- Permissions in v1: `files.read`, `files.write`, `files.shares`, `notifications`, `directory.read`, `network.internet`, plus the elevated rights of D71 under `backend.elevated`. In 1.0 `docker.socket` and `host.full` are refused with `app.elevated.unsupported` (A16).
- Icon: a square viewBox, at most 64 KB; no `<script>`, `foreignObject`, `on*` attributes, external `href`, `<image>`, or `@import` and `url()` in styles. What matters belongs in the inner 80 percent, because the desktop rounds the corners. Without an icon of its own an app shows the default icon, the Pithyx box glyph on a neutral tile (D307).

Compose subset (contract in A6, D310):

- Allowed: `image` with `@sha256`, `command`, `entrypoint`, `environment` without `$` interpolation, `working_dir`, `volumes` (declared names and tmpfs only), `depends_on`, `healthcheck`, `expose`, `read_only`, `init`, `stop_*`, `shm_size` (capped), `labels`.
- Refused: `ports`, `privileged`, `network_mode`, `pid`, `devices`, `cap_add`, `build`, `networks` and everything else, unless the matching elevated right is declared; the check runs in both directions (a right without its compose key is an error too).
- Volumes: a named volume with the id of a `storage` request is mapped to the folder the administrator assigned (read-only or read-write); every other named volume is a folder in the app's dataset.
- The daemon rewrites the file before use: project name `pithyx-<id with _>`, the app's network, `user` and `group_add`, the journald log driver, mounts, `pids_limit` and `oom_score_adj`, labels `com.pithyx.*`.

#### SDK API v1 additions (contract in A4)

```ts
// Context, without any permission: user {id, name, displayName, groups[], isAdmin, twoFactor}, language, formats,
// time zone, theme, box {name, version}, visible, online, logLevel, backend {status, endpoints} | null,
// storage[{id, state, access}]. All users and groups only with directory.read (D304).
app.backend.url(path, { endpoint? }) / app.backend.fetch(path, init & { endpoint? }) / app.backend.socket(path, { endpoint?, protocols? })
app.backend.token()                                // replaces auth.token
app.directory.users() / app.directory.groups()     // only with directory.read
app.log.log(...)                                   // alias of info; every level also goes to the browser console
app.notify({ ..., actions?, data?, tag? })         // action buttons
app.setBadge(count | null)                         // counter on the taskbar entry
app.window.requestAttention()                      // pulses, never takes the focus (guardrail 7)
app.window.setDirty(dirty)                         // beforeClose asks only while there are unsaved changes
app.contextMenu.show(at, items)                    // the desktop draws the menu
app.clipboard.writeText(text)                      // the iframe has no Clipboard API over plain HTTP
app.openUrl(url)                                   // new tab, noopener
```

New events:

| Event                                                            | Why                                                                                                               |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `visibilityChange {visible}`                                     | Minimizing a window in the desktop does not change the iframe's visibility.                                       |
| `connectionChange {online}`                                      | The box cannot be reached, for example while it restarts.                                                         |
| `backendStatus {status}`                                         | `stopped`, `starting`, `running`, `updating`, `unavailable`. Replaces `backendUnavailable` and `backendRestored`. |
| `permissionsChange {permissions}`                                | Replaces `permissionRevoked` and also covers new grants.                                                          |
| `storageChange {storage}`                                        | A mapping changed, or its pool was locked or came back.                                                           |
| `notificationAction {notification, action, data}`                | Without an open window the app starts with `launch.notification`.                                                 |
| `logLevelChange {level}`                                         | An administrator switched debug on or off.                                                                        |
| `filesDropped {files, x, y}`                                     | Deferred to 1.1 (A4).                                                                                             |
| query `beforeUnload {reason: logout, shutdown, restart, update}` | Replaces `beforeLogout`. No veto, 2 seconds.                                                                      |

Refused: `resize` (a ResizeObserver in the iframe is enough), `idle` and `clipboardChange` (privacy).

Planned with the owner on 2026-10-08 (D328, D329); it replaces the draft of 2026-10-03 and answers its two open decisions. Built after A15 and before A16 and A17, so the new manifest fields are part of SDK 1.0.0. Waves W5a to W5c; the working rules of the app steps apply (D313).

Trust and sources (D328):

- System apps (Files, Settings, Store and the rest) stay in the OS image and update with OS releases; they are in no catalog.
- Two catalogs of the project, both made from `pithyx/catalog-template`: `pithyx/apps-official` (tab "Official", badge "Pithyx", the only catalog that may ship `org.pithyx.*`) and `pithyx/apps-community` (on by default since D343, the owner's wish of 2026-10-10; an administrator switches it off, and on again after a warning). Custom catalogs (tab "Own") and sideloads are administrators only and flagged unverified; custom catalogs are never signed and follow the global update policy.
- A catalog repository has three branches: `master` holds the source of every app in `apps/<id>/` (pull requests, the owner's review, `maintainers.json` names who may update an app, any OSI license by SPDX id); `catalog-next` and `catalog` are written only by CI and hold per app and version the manifest, icon, screenshots and the built `.pithyxapp` without images, plus `index.json` and its signature. The box never builds anything (D301).
- After a merge, CI builds the frontend and every backend image from the merged commit and pushes the images to `ghcr.io/<owner>/apps/<id>/<service>:<version>`; packages link them only by digest. A published version is never overwritten or deleted.
- The build job runs the app's code without write rights or secrets; a separate publish job pushes the built OCI layouts, pins, locks, packs and commits to `catalog-next`, and runs no code of the app. Pull request runs from forks start only after the owner's approval.
- `index.json` is signed with Ed25519: `catalog` by a key in the GitHub environment `catalog-release` that a promote job uses only after the owner approves it, `catalog-next` by a separate `next` key that the box trusts only on the beta channel. The public keys are built into the daemon (more than one, for rotation). `sequence` only grows; a box refuses an older index.
- The box keeps a shallow copy of every enabled catalog in `/var/lib/pithyx/catalogs/<id>/` (on the system disk like apt's lists, so the Store works before an app pool exists or while it is locked), fetches it at the check time and verifies it; on a failure it keeps the last verified copy.
- Private catalogs: the box makes an SSH deploy key per catalog and shows its public key; an optional read token pulls private images.

Updates and settings (D329):

- The Store's gear opens its settings: the update policy (automatic, notify, nothing; default notify) with a per-app override, the check time (default 03:00 in the box's time zone plus a random delay of up to 60 minutes) and "check now", desktop notifications to administrators (other channels later), the catalogs (community on or off, stable or beta channel, custom catalogs with URL and SSH key), and installing from a file.
- An update that asks for new permissions or elevated rights never installs automatically.
- The snapshot taken before an update stays until the next update, with the previous version's folder and images, so "back to version x" restores app and data together. A real downgrade from a catalog needs the same `dataVersion` in both manifests.
- Tabs: Installed, Updates (only while there are updates, with a count), Official, Community (when on), Own (when a custom catalog exists). The detail page shows screenshots, author, license, permissions and links to the homepage and to the app's source in the catalog.

Guardrails (set by the owner on 2026-09-27, binding like `CLAUDE.md`; the spec and every later SDK change follow them):

1. Apps never see cookies, the session or the desktop DOM. Third-party apps always run in the sandboxed iframe. Permissions are checked on the server.
2. Core apps use the same API as third-party apps; only the transport differs.
3. Permissions are declared in the manifest, confirmed by an administrator and revocable (`permissionRevoked`).
4. SemVer on the SDK interface. Deprecations last one major version.
5. Everything is async. Errors are RFC 9457 problems with a code and params.
6. Theme, accent, locale and density reach apps as CSS variables plus events. `@pithyx/ui` stays optional.
7. Apps control only their own windows. No focus stealing without a user action.
8. App backends are reached through YARP; their only identity source is `X-Pithyx-User`.
9. File access only through the SDK file API. File types for `openFile` are declared in the manifest.
10. Not in v1: app-to-app communication, background tasks without a window, widgets.
11. The SDK provides the locale and formatters, plus an optional i18n helper for ICU JSON. Apps may bring their own i18n.
12. Named storage requests in the manifest. An administrator maps them to real shares; the app never sees real paths.
13. Elevated rights are allowed, each named on its own (`docker.socket`, `host.network`, `device:<path>`, ..., `host.full`). They apply to the backend container only. Installing needs plain-language risk text plus password (and TOTP), by administrators only. New rights in an update need a new confirmation. A permanent badge, an audit log entry, revocable. ## Step 7: Storage safety foundation

Effort: high.

Goal: the daemon sees real pools on the dev VM and cannot write to a disk it must not touch. Nothing in M3 writes to a disk before this step is done.

### 7.1 Real mode on the dev VM

- [x] A dev systemd unit runs the daemon as root in real mode on the dev VM (simulation stays the default for E2E and local development). `/etc/pithyx/environment` decides `dev` or `prod`; a missing file means `prod`. (`tools/dev-vm/pithyx-dev.service` with `install-dev-daemon.sh`; the owner installs it, since agents may not install system units.)
- [x] `IStorageBackend` (one of the two allowed abstractions) with ZFS as its first implementation; mdadm and btrfs come later through the same interface (D111).
- [x] Parsers for `zpool status -j`, `zpool list -j`, `zfs list -j` and `zfs get -j` (OpenZFS 2.3 JSON output) as pure functions with fixtures recorded on the dev VM with `tools/fixtures/record.sh` (single disk, mirror, raidz1, degraded, resilvered, scrub paused and finished, no pools). - [x] `SystemStateService` keeps pools and datasets in memory, refreshed from `zpool events -f` (streamed, no polling) and at startup. `GET /api/storage/pools` reads from memory; topic `storage/pools` pushes changes.

- [x] `DiskGuard` as a pure decision function over the lsblk tree, the mount table and `/etc/pithyx/*`:
  - The system disk (anything holding `/`, `/boot`, `/boot/efi`, swap or `/var/lib/pithyx`) is always refused, with no override.
  - In `dev`, only disks whose serial is listed in `/etc/pithyx/test-disks` are allowed.
  - In `prod`, a disk must be empty (no partitions, no filesystem or RAID signatures, no ZFS labels, not part of an imported pool). Otherwise the user must confirm with the disk's serial number.
- [x] Command plans: every destructive action is first built as a list of exact commands, shown to the user, logged with the request id, and only then run as a job. The job re-checks `DiskGuard` right before each command, because disks can change in between. (Step 7 builds, shows and tests plans; `CommandPlanRunner` gets its endpoint and job in step 8, so nothing destructive runs yet.)
- [x] Pools are never imported automatically, never with `-f`, and never as a side effect of recovery ("Recovery never modifies pools automatically"). Import is an explicit action in step 8.

### 7.3 Settings app shell

- [x] Settings as a core app on the SDK (in-process transport, its own chunk loaded with `import()`), with pages Storage, Users, Shares, Network and Energy that later steps fill. Administrators only; the start menu and the desktop link to it. (Owner's rule: only finished pages ship, so step 7 has Storage alone. Its administrator calls are the internal `internal.admin.storage.*` methods of `desktop/src/apps/sdk/internal.ts`, not part of `@pithyx/sdk`.)

### 7.4 CI (D109)

- [x] `CLAUDE.md` (Tests) says integration tests run on GitHub-hosted runners with file-backed vdevs and loop devices, and that the destructive suite runs on the dev VM before a storage PR is merged.
- [x] A `storage` CI job that runs only when storage code changes (path filter in `changes`): installs `zfsutils-linux` on the Ubuntu runner, creates pools on sparse files and loop devices, and runs the integration tests against them. Each run is a fresh VM, so nothing survives it.

### Test on the dev VM

- Pools created with `testpool.sh` appear in the API and the topic without a reload; `zpool offline` on a test disk updates the state live.
- Every command plan against `sda` (the system disk) or a disk that is not listed as a test disk is refused, also with a correct serial typed as confirmation.
- A plan for a VYXTEST disk lists the exact `zpool` commands; nothing runs until it is confirmed.

### Must never happen

- A write to the system disk or, on the dev VM, to any disk that is not a VYXTEST disk.
- `zpool create`, `zpool labelclear`, `wipefs` or a partition change that did not pass `DiskGuard` right before it ran.

### CI

- Golden tests of every command plan (exact argument lists).
- Parser fixture tests; the `storage` job on file-backed pools.

**Done when:** the daemon on the dev VM runs in real mode, shows the test pools live, refuses every destructive plan outside the VYXTEST disks, and the `storage` CI job is green.

## Step 9: Encryption and key vault

Effort: high. Moved after v0.2 (owner's decision on 2026-09-30, see "Release 1.0").

Goal: pools can be encrypted, unlock after a power loss if the owner wants that, and nobody gets at the data without the key. Real data goes on Pithyx pools only after this step.

- [ ] ZFS native encryption per pool (D106, decided): the encryption root is `<pool>/pithyx`, so everything Pithyx stores on the pool is encrypted with one key. Encryption per share can follow later.
- [ ] After creating an encrypted pool, the key must be downloaded or printed and its storage confirmed before the pool can be used, like the recovery key in setup.
- [ ] Unlock manually with the key, automatically from the key vault on the system disk (root only, mode 0600, never in a support bundle), or from a USB key. The UI explains that the key vault protects against stolen disks, not against a stolen box.

- [ ] Change the key (`zfs change-key`) only after the new key is saved and confirmed; the old key keeps working until then.
- [ ] Secrets (keys, passphrases) are masked in every log and never written to the pool itself.

- A key in a log, a support bundle or on the pool.
- A key vault file readable by anyone but root.

## Interfaces for M4

M3 builds these so M4 (apps) uses them without rework. M4 itself is not part of M3; it is "Apps 1.0 (SDK and runtime)" since D300 (storage mappings in A10 and A14, app uids in A10, datasets in A10, permissions in A10 and A11, availability in A14).

- Named storage (SDK guardrail 12): M3 provides shares as datasets with grants and an internal daemon API that resolves a share and a relative path to a mount path. M4 adds `storage_mappings` (app, storage id, share, subpath, access) on top and bind-mounts the folder into the backend at `/pithyx/storage/<id>`. A window's effective access is the lesser of the manifest's access and the user's share right; the backend's access comes from the share groups.
- Users: `X-Pithyx-User` carries the stable, Linux-valid user name and the user id. Each app backend runs as its own uid and gid from the app range that M3 reserves (40000 to 49999, same allocator), mapped through userns-remap. An app reaches shares only as a member of the share groups from step 11, never with a user's uid.
- Datasets: one per app under `<pool>/pithyx/apps/<id>`, mounted at `/<pool>/.pithyx/apps/<id>`, with a quota. Before every update a snapshot `pithyx-preupdate-<version>` with a hold, and a rollback when the update fails. M3's dataset, quota, snapshot and hold API carries no share assumptions for this.
- Permissions: grant subjects are `user`, `group` and later `app`; "app allowed" is already a resource in M3. M4 adds manifest permissions as their own table but uses the same resolver, the same checks on every request and the same push on revoke.
- Availability: M3 publishes when a pool or dataset is locked or missing; M4 refuses to start apps with mounts on it and shows why.

- **D290** (high, 2026-10-03) The permission model for 1.0 (step 11). Rights are rows of `grants` (migration 0020): a subject (`user`, `group`, `app` for M4) and a resource (`share:<id>` with `read` or `readWrite`; `protocol:smb|sftp|webdav|ftp`, `app:files|viewer|demo`, `right:admin|desktopLogin|sshLogin|power` with `allow`). `PermissionResolver` is a pure function: a user gets the union of its own grants and those of its groups, the built-in group `users` included; administrators have everything; a deactivated user nothing; there are no deny rules (table and property tests). A change of rights re-authorizes every open WebSocket, pushes the user's rights on the per-user topic `session/permissions` (the desktop closes windows of apps no longer allowed and hides them) and ends the connections and sessions of users without the desktop login right (`auth.desktop.not_allowed` at sign-in, only after the right password). On disk (D102 on top of D286) every dataset share has two Linux groups `pithyx-s<id>-r` and `pithyx-s<id>-rw` with gids from the group range, the ACL names only them, and a change of rights changes their members (`gpasswd`) instead of walking the files; the share's folder is compared with `getfacl` at every reconcile and set again on a difference. Like any supplementary group, a new membership applies to the next login of SMB and SFTP sessions. SMB `valid users`/`write list` and the SFTP views follow the effective rights. SSH logins are a setting in File services (off by default): users with `right:sshLogin` get `/bin/bash` and the sshd group `pithyx-ssh` (password, no forwarding) and no SFTP view; Pithyx never stops sshd, so switching it off cannot lock an administrator out of the box.
